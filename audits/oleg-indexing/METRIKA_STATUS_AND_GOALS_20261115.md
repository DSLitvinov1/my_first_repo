Не считать клик `Отправить` подтверждением CRM.

## Подготовленный продукт: события для обеих площадок

В кабинете каждого счётчика создать **по четыре цели типа «Целевое событие»** (условие «идентификатор совпадает»). Настройка на обоих счётчиках имеет одинаковые идентификаторы, статистика изолирована отдельными counter ID.

| Название цели | Идентификатор | Что означает |
|---|---|---|
| Клик по телефону | `oleg_phone_click` | Пользователь выбрал ссылку `tel:` |
| Клик по электронной почте | `oleg_email_click` | Пользователь выбрал ссылку `mailto:` |
| Открытие юридического помощника | `oleg_consultation_open` | Пользователь открыл помощника и увидел панель |
| Открытие CRM-формы | `oleg_crm_form_open` | На сайте показана именно своя форма Битрикс24 |

- Это **цели интереса**, а не подтверждённые продажи/заявки. Не складывать число целей в «количество реальных лидов»; один посетитель может выполнять несколько действий.
- Событие `oleg_lead_success` **не отправляется и пока не должно настраиваться как действующая конверсия**: его источник — проверенное подтверждение сделки/лида в Битрикс24. Для CRM-интеграции потребуются доступ к записи и документированная схема корреляции событий или офлайн-конверсий.
- Модуль `oleg-metrika-goals-v1.js` не собирает имена, телефоны, описания юридических вопросов, не сохраняет персональные данные и не обходит согласие; работает только на двух доменах и с их счётчиками.
- [Playwright test #43727461119](https://github.com/DSLitvinov1/my_first_repo/actions/runs/43727461119): **48/48 checks PASS** на двух сайтах × мобильный/десктоп. Трафик в Яндекс блокировался, формы CRM не отправлялись. Код был динамически вставлен в тестовый браузер, не на живой сервер.

## Безопасная публикация (подготовлено, но не выполнено)

- `apply_metrika_goals.py`: строгая проверка исходников действующих двух сайтов в **авторизованной** директории размещения. Добавляет код к действующим двум JS без изменения существующей логики согласия.
- Изменяет суффиксы версий `?v=` на **25+20** HTML-страницах, чтобы браузер сразу получил новую версию аналитики; проверяет исходные версии, число страниц, отсутствие лишних счётчиков и символических ссылок.
- По умолчанию только сухая проверка, публикация через явное действие. Перед любыми изменениями создаёт резервную копию каждого файла, блокирует устаревшие файлы и проверяет байты после записи. Протестировать окончательный прогон в GitHub Actions.
- **Фактически на сайтах не опубликовано:** подключённая здесь GitHub-ветка является аудитом и исходником патча; нет прав записи в Timeweb и браузере через текущий ChatGPT.
- После публикации нужно запустить Playwright E2E повторно **против опубликованного кода без `addScriptTag`**, проверить каждое событие с заглушённым Яндекс-трафиком и сверить ответы Метрики в её кабинете. Затем создать 8 целей в интерфейсе и проверить реальные цели уже без заглушки в согласованной тестовой сессии, не записывая реальные PII.

## Ограничения и следующий точный этап

1. Предоставить управляющий доступ к текущей авторизованной вкладке Метрики в ChatGPT **Work** или через собственный локальный Playwright, не открывать вкладки заново и не передавать пароли. Чат-режим `Browser` имеет только чтение вкладок и блокирует хост.
2. Проверить наличие существующих целей (возможно автоцели и вручную созданные), избежать дублей; затем добавить недостающие четыре типа `Целевое событие` для каждого счётчика.
3. Подключить разрешённый хостинг в реальной сессии, опубликовать защищённый пакет и перепроверить кэш, мобильное отображение, URL источников, ошибки, логирование и согласие.
4. Лишь после подтверждения CRM-обращений и их источников вводить отдельную цель «Получена заявка»; ранее отправленные тестовые формы не имеют подтверждённого CRM-readback. Не создавать новые обращения вслепую.
5. Яндекс Директ не запускать.
