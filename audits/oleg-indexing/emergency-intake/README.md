# Олег — аварийный приём юридических обращений V17

**Версия: только подготовка и испытания. На действующих сайтах не опубликована.**

## Назначение

Публичные формы Битрикс24 двух сайтов периодически не отрисовывались в браузере, хотя HTTP GET возвращал 200. Отдельные исторические сделки №10 и №12 подтверждают, что существующие формы способны создавать сделки, но не гарантируют их постоянную доступность.

В V17 подготовлен отдельный резервный приём обращений на собственном Timeweb. Он не зависит от загрузки внешнего JavaScript Битрикс24. Никаких новых платных сервисов не требуется.

## Состав

- `public/emergency-lead.php` — минимальная серверная форма. Только имя, телефон и краткое описание, обязательное согласие со ссылками на **существующие** `/consent.html` и `/privacy.html`. Интерфейс работает без JavaScript.
- `private/intake-core.php` — шифрование Sodium Secretbox, SQLite/WAL с `synchronous=FULL`, ограничение размера, CSRF, контроль Origin и сеанса, honeypot, ограничение частоты, атомарная запись и идемпотентность.
- `private/console.php` — установка в закрытый каталог, сводка количества, список непрозрачных квитанций без ПДн и чтение одной квитанции **только локально по явному флагу с предупреждением**. Использование для CRM требует оператора; автоматического экспорта в Битрикс24 нет.
- `build_hotfix.py` — только локальный построитель **четырёх** файлов: две действующие главные страницы и два `legal-assistant-v4.js`. Сверяет все оригинальные SHA256 и отказывается работать при дрейфе. Кнопка резервной формы добавляется непосредственно рядом с ссылкой на Битрикс24, телефоном и почтой. Старые нерабочие `data-form-mode=demo` формы остаются выключенными.
- `tests/` — Python unit- и HTTP-integration проверки на вымышленных данных в `/tmp`, без реальных CRM заявок.

## Точная семантика успеха

**«Обращение сохранено на сервере» означает только SQLite COMMIT** и выдачу непрозрачной квитанции. Этот статус **НЕ** означает отправку в Битрикс24, просмотр юристом, доставку email, SMS или push. Любая ошибка записи даёт HTTP 503/4xx без ложного подтверждения. При недоступности Битрикс24 данные остаются в зашифрованной очереди до ручной обработки.

Отдельно требуется регулярная проверка очереди ответственным сотрудником, подтверждённый процесс переноса в CRM и уведомление о новых ожидающих обращениях. **Без этого продакшен-приёмка не завершена.**

## Испытания

17.11.2026 на **реальном Timeweb, но только в изолированном каталоге `/tmp`**, выполнен Python HTTP test suite с PHP 8.2, SQLite и Sodium:
- действительная запись и получение номера подтверждения после коммита;
- шифрование текста и телефона в базе, права 0700/0600;
- повтор того же запроса не создаёт вторую запись;
- изменённые данные при прежнем ID дают 409;
- посторонний Origin, неверный CSRF, honeypot, отсутствующее согласие отклоняются;
- браузер без Origin, но с верным CSRF работает;
- лимит 5 обращений с IP за 20 минут;
- отсутствие базы возвращает 503, а не сообщение об успехе;
- другой домен не может использовать форму;
- локальное чтение расшифровки требует явного `--confirm-sensitive`.

Последний запуск: `V17_INTAKE_ISOLATED_TESTS_PASS`, продакшен-записей 0. Дополнительно **14/14** Python unit-тестов интерфейса, `php -l` для всех файлов и `node --check` для обоих подготовленных JS: PASS.

## Границы внедрения: до разрешённого production release

1. **Ревизия согласий и 152-ФЗ** с Олегом, в том числе оператор данных, срок хранения, необходимость российской локализации и доступ сотрудников.
2. Настроить резервную копию зашифрованной SQLite-базы **и отдельно ключа Sodium**, проверить восстановление в закрытом тестовом каталоге; определить утверждённый срок хранения и безвозвратное удаление по регламенту.
3. Проверить, что PHP-FPM обоих реальных сайтов может обращаться к одному общему каталогу вне webroot (на Timeweb с `open_basedir` могут отличаться ограничения от PHP CLI). Проверить HTTPS, правильное имя домена и работоспособность формы при отсутствии Bitrix CDN.
4. Проверить систему оповещения дежурного о **необработанных резервных заявках** без передачи ПДн в открытые уведомления. Подтвердить, кто и как открывает их по защищённому каналу и переносит в CRM с независимым readback.
5. Перед публикацией перепроверить действующие SHA **4/4** и права владельца, создать свежий backup двух сайтов; внести отдельную доступностную правку **без** 43-файлового SEO-пакета. Сначала установить защищённую серверную часть, проверить её; только затем публиковать ссылки на неё. Для каждого сайта нужен проверяемый откат. **Изменения production требуют отдельного согласования.**
6. После rollout проверить формы на двух доменах, обычный и мобильный браузер, отказ Битрикс24, восстановление, дубли, передачу резервной заявки в CRM, уведомление Олега. Тестовые отправки — только после согласования.
7. Только после приёмки подачи заявок отдельно проводить предварительно согласованную атомарную публикацию SEO V13–V15.
