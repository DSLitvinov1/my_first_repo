# OPS → будущий интерфейс «Нейрозавода». Контракт состояния, версия 1

Статус: собственный изолированный кандидат OPS. Координаторская схема — `MVP_READ_ONLY_INTERFACE_CONTRACT_20261015_RU.md`, задача №6; передача на согласование в Issue №3. **Это не эксплуатационная интеграция**.

## Реализация

Вызываемая функция `snapshot_to_status(snapshot)` в `status_adapter.py` принимает **один явно переданный офлайн-снимок** и возвращает самостоятельный JSON-объект `neurofactory.ops.status_view`. Параллельно доступен текстовый русскоязычный вывод.

Прямого опроса GitHub, API, Windows, bridge, очереди, CORE/PROVIDERS или checkpoint нет. Для получения реальной телеметрии владелец источника должен передать заранее сформированный минимальный снимок в согласованном формате; живой сбор в будущем требует отдельного решения координатора и настоящей независимой проверки.

## Входная модель

Верхний уровень строго: `schema=1`, `scope=neurofactory-ops-status`, `observed_at` с явным часовым поясом, `project`, `bridge`, `workers`, `queue`, `runs`, `problems`.

- **project:** фиксированный ID безопасного sandbox-проекта, репозиторий owner/name, ветка и точный 40-символьный SHA. Чужие произвольные поля запрещены.
- **bridge:** заявленный RUNNING/IDLE/FAILED/OFFLINE/UNKNOWN и время heartbeat. Без heartbeat или спустя более 300 секунд отображение UNKNOWN.
- **workers:** ID, роль, заявленный статус, heartbeat и GitHub run ID или null. Не более 50.
- **queue:** до 100 задач с task ID, статусом QUEUED/CLAIMED/RUNNING/BLOCKED/CHECKED/UNKNOWN, исполнителем, числом попыток, временем последнего прогресса, состоянием checkpoint и GitHub run ID. Для RUNNING/CLAIMED без прогресса свыше 900 секунд выводится предупреждение POSSIBLY_STALLED. При PARTIAL checkpoint задача отображается BLOCKED, но никакого автоматического восстановления нет.
- **checkpoint:** VERIFIED/PARTIAL/MISSING/UNKNOWN, SHA-256 или null, заявленный durable_readback. Даже внутренне согласованный VERIFIED в пользовательском снимке **никогда не становится внешне подтверждённым**.
- **runs:** до 60 GitHub Actions наблюдений — run ID, статус, исход, exact source SHA. URL составляется только из синтаксически проверенного owner/name и положительного run ID. Это удобная ссылка для ручного открытия GitHub, а не доказательство подлинности.
- **problems:** код ошибки из закрытого перечня, task ID/null, run ID/null. Повторы группируются по коду и задаче, считаются только **различные номера из входа**, а не аттестованные внешние события.

## Выход для интерфейса

Объект `neurofactory.ops.status_view` содержит `project`, `source`, `bridge`, `workers`, `queue`, `queue_counts`, `checkpoint_counts`, `runs`, `problems`, `integrity`, `actions_allowed`, `limitations`.

Для каждого состояния отдельно: `reported_state` (что заявил снимок) и `display_state` (консервативная интерпретация). Отсутствие данных/устаревший heartbeat = **UNKNOWN**, а не «всё работает». Все ссылки на GitHub и отметки времени остаются непроверенными до внешней read-only сверки; `source_verified=false`, `snapshot_authenticated=false`.

Все права по умолчанию и навсегда для этого изолированного адаптера: restart=false, retry=false, recover=false, publish=false, merge=false, send_chatgpt=false.

## Безопасность

- Только локальный входной JSON до 500 KB, без дублей ключей.
- Выделенный `secure_input.py` использует pinned-dirfd и O_NOFOLLOW на Linux/macOS; на Windows проверяет reparse/symlink и идентичность файла. Доверенная Windows директория и отсутствие конкурентной подмены со стороны той же учётной записи остаются обязательным ограничением.
- Нет обращений к сети, subprocess, журналам очереди, личным файлам, секретам и рабочему Windows-мосту.
- Разрешена только аналитика заявленных данных. Ни один сохранённый результат не может заменить независимого REVIEW/координатора или открыть выпуск.
- Пример `examples/ui_status_example_20261015.json` **синтетический** (в том числе искусственная BLOCKED-задача). ID исторического GitHub-run в нём — не доказательство состояния задачи.
- Интеграция в UI Issue №10 возможна только после официального принятия интерфейсного контракта координатором и независимой приёмки OPS Issue №6.

## Условия следующего этапа

1. Координатор «чат 3» проверяет совместимость указанных полей с CORE Issue №9 и будущим UI Issue №10, при необходимости присылает узкие замечания в Issue №3.
2. Независимый проверяющий, не являющийся OPS-автором, проверяет точный коммит и негативные сценарии в Issue №6.
3. Следующий read-only live-collector рассматривается **отдельно**: публичный GitHub metadata API с подтверждёнными правами, временем, источником, ошибками сети и лимитами. До согласования этой возможности нет.

Сохранение ветки, собственные тесты и положительный CI не дают прав на merge, создание задач, восстановление или отправку в ChatGPT.

## Согласование двух уровней с координатором (Issue №3, ответ №6180004734)

По решению координатора защищённая сводка **всех направлений** из DRAFT PR №12 и подробная диагностика **отдельного проекта** из OPS — разные источники, которые запрещено считать взаимозаменяемыми. Создан собственный адаптер `ui_readonly_bundle.py`: принимает уже сформированный документ `read_only_coordination_board` и/или подробный локальный OPS snapshot. Чужой код координации в OPS не импортируется, не копируется и не изменяется. Отсутствие одного из документов отображается отдельным UNKNOWN.

Формат `neurofactory_ops_ui_readonly_bundle`, версия 1:
- `board.lanes`: заявленная фаза CORE/PROVIDERS/COORDINATOR/REVIEW/OPS/SKILLS/UI/HANDOFF/GODMODE, exact SHA и ссылка на GitHub Issue/PR с `not_verified`. Для HANDOFF допускается только `paused` или `unknown`.
- `project_detail`: Windows-мост, исполнители, очередь, checkpoint, проблемы, последнее заявленное успешное исполнение, последний заявленный отказ, остановленные и предположительно зависшие задачи.
- `consistency.board_project_match`: true/false/null для совпадения **заявленных** OPS repo+branch+SHA между двумя слоями. Совпадение не является независимой аттестацией, несовпадение не маскируется.
- `trust`: `live_source_verified=false`, `independent_review=false`, `release_authorized=false`, `all_sources_untrusted=true`.
- `actions_allowed`: все операции запрещены.

Сырые статусы `RUNNING` остаются только в `reported_state`; если heartbeat не получен из независимо заверенного источника, отображаемый оперативный статус `display_state=UNKNOWN`. Для частично сохранённого checkpoint и заявленной остановки используется осторожное `BLOCKED`. Срабатывание по возрасту активности говорит только о **возможном** зависании внутри снимка. Ни даты настоящего момента, ни фактическое состояние Windows-моста система не узнаёт.

Сводка `run_highlights` выбирает максимальный заявленный GitHub run ID для success/failure **только при совпадении exact SHA с проектом**. ID сортирует недоверенные записи, а не подтверждает реальную хронологию или результат GitHub. Когда успешных или ошибочных запусков в предоставленном снимке нет, используется null/UNKNOWN. Нет какого-либо автоматического скачивания или доступа к рабочим приватным репозиториям.

Для воспроизводимого примера: `examples/ui_two_layer_lane_board_synthetic.json` — полностью синтетическая сводка направлений, `examples/ui_status_example_20261015.json` — синтетический проектный статус. Пример не подтверждает состояние работающих чатов. CLI умеет читать оба документа из локальных файлов с защищённым чтением и выдаёт JSON.

**Граница согласования:** сообщение координатора №6180004734 подтверждает разделение двух слоёв и необходимость минимального адаптера, но НЕ означает разрешённый production UI, live-source API или независимую проверку. Даже успешный тест локального объединения не снимает запреты Issue №6, Gate A/B/C/D, HANDOFF pause и отсутствие независимого REVIEW.

## Критерии завершения этапа OPS — приёмочный чек-лист

Это **условия приёмки OPS**, а не объявление его завершённым. Различаются:
- **OPS MVP функционально готов к независимой приёмке**: работает автономный офлайн-адаптер и имеются собственные адресные тесты, но он не подключён к настоящей очереди.
- **OPS MVP независимо принят**: помимо функций получены действительные независимый verdict и решение координатора для точного коммита.
- **OPS как рабочая подсистема завершён**: имеется одобренный безопасный актуальный источник данных и проверена работа end-to-end **только для чтения**; интеграция санкционирована отдельно. Не путать с завершением пятого этапа всего «Нейрозавода».

Все критерии ниже обязательны; отсутствие подтверждения = NOT_DONE. Состояние «неизвестно» не считается ни успехом, ни отказом.

### A. Функциональная готовность автономного MVP

- [ ] По одному строго ограниченному входному снимку OPS выдаёт единый машинный JSON и русскую читаемую сводку для будущего интерфейса. В документе есть project ID, exact Git SHA, ссылка/состояние источника, время наблюдения, Windows-мост, исполнители, задачи, контрольные точки, обнаруженные проблемы и причины блокировок.
- [ ] При наличии соответствующих заявленных данных правильно отбираются **последний успех**, **последний отказ** и последний результат по **одному exact source SHA**, не смешиваются результаты других коммитов; выбор по максимальному ID во входе явно маркируется как недоверенный, а не доказанная хронология GitHub.
- [ ] Обнаруживаются заявленные BLOCKED, PARTIAL, UNKNOWN, возможные зависания по времени без прогресса, повторяющиеся ошибки по различным run ID. Дубли, повреждённые или противоречащие друг другу записи не дают ложноположительный успех.
- [ ] Отсутствующий, устаревший или неподтверждённый heartbeat всегда приводит к отображению UNKNOWN для «живого» RUNNING, с отдельным сохранением заявленного значения. Никаких выдуманных исполнителей или пустой очереди «все работают».
- [ ] Два слоя будущего UI — `read_only_coordination_board` и `neurofactory.ops.status_view` — принимаются независимо; отсутствующий слой помечается UNKNOWN, несовпадение repo/branch/SHA показывается явно, совпадение не становится подтверждением подлинности. Утверждённый координатором контракт не изменяется молча.

**Доказательства A:** отдельные вызовы программ на синтетических и разрешённых обезличенных образцах, фиксированный JSON/text-вывод, адресные тесты с привязкой к exact SHA. Синтетический пример не доказывает реальное состояние машин.

### B. Безопасность и отсутствие побочных действий

- [ ] Защита входа: ограничение размера, корректный UTF-8, запрет двойных JSON-ключей, проверка схемы и идентификаторов, невозможность через символические ссылки, reparse-point, FIFO или путь получить недозволенные локальные файлы. Ограничение Windows same-user directory race документировано и передано независимому аудитору.
- [ ] Не используются платные API, сетевые вызовы к действующим исполнителям, секреты, запуск процессов, изменение чужих веток/файлов/очереди/контрольных точек или Windows-мостов. Все операции restart/retry/recover/publish/merge/send_chatgpt недоступны.
- [ ] Поддельные APPROVE, GitHub run ID, digest, heartbeat и checkpoint-«VERIFIED» не повышают доверие, не разрешают выпуск и не раскрывают секреты в отчёте. Любая неопределённость исхода публикации = STOP/UNKNOWN, а не повторная отправка.

**Доказательства B:** собственные негативные тесты новых изменений и самостоятельная проверка проверяющим, diff только по префиксам OPS.

### C. Проверенные испытания и происхождение

- [ ] Точный HEAD кандидата зафиксирован в GitHub; на **этом же** HEAD пройдены адресные критические тесты Linux и Windows. В отчёте есть ссылки на run/jobs и точные числа успешных, пропущенных и неуспешных тестов. Исторические 20 виртуальных машин на старом SHA не засчитываются за новый.
- [ ] Все обнаруженные блокирующие дефекты исправлены только в файлах OPS и перепроверены на новом точном коммите. Нет неразобранных P0/P1 ошибок и нарушений области владения.
- [ ] Независимый аудитор **не автор OPS и не владелец зарезервированного CORE REVIEW** выдаёт проверяемый APPROVE по точному HEAD, с собственной ссылкой на воспроизводимые evidence в GitHub Issue №6. Самопроверка и успешный авторский CI не заменяют verdict.

**Доказательства C:** GitHub compare, SHA, CI конкретного SHA, независимый отчёт, отдельное однозначное решение в Issue №6.

### D. Согласование интерфейса и разрешение координатора

- [ ] Координатор «чат 3» письменно подтвердил точные поля и совместимость с отдельной сводкой направлений из PR №12 и будущим UI Issue №10; при замечаниях изменения согласованы и проверены адресно.
- [ ] Координатор после независимого APPROVE дал **отдельное** разрешение на конкретный следующий шаг: offline pilot или ограниченный read-only источник. Сам комментарий или тест не даёт прав на merge, live polling, production или выпуск.

**Доказательства D:** прямые ссылки на решения в GitHub Issue №3 и собственную контрольную точку exact SHA.

### E. Только для закрытия OPS как рабочей подсистемы, а не офлайн-MVP

- [ ] После согласования внедрён **разрешённый только для чтения** источник с актуальными метаданными GitHub (или явно разрешённый feeder от владельца очереди), в котором для каждого показания есть источник, время, exact commit, readback/status/ошибка API. Нет доступа по записи и нет молчаливого перехода на привилегии чужих компонентов.
- [ ] На разрешённом учебном/sandbox примере проверены и показаны: действительно подтверждённый успешный запуск, отказ, неизвестный исход, блокировка, возможное зависание и checkpoint. Для очереди/моста без утверждённого источника в UI остаётся UNKNOWN.
- [ ] Подтверждена безопасная передача того же выходного формата UI без утечки секретов, с корректным отказом при потере связи, истечении актуальности, отсутствии прав, ошибке API или подмене происхождения. Выполнена независимая проверка этих новых интеграционных изменений и отдельное разрешение координатора.

**Доказательства E:** ограниченный интеграционный CI/пилот на **новом exact SHA**, независимый отчет и явный допуск координатора. Не выполнять E до разрешения.

### Итоговая процедура

- **A+B+собственные части C** → `FUNCTIONAL_CANDIDATE`; честно сообщать, что данные офлайн и приёмка отсутствует.
- **A+B+C+D полностью** → `INDEPENDENTLY_ACCEPTED_OFFLINE_MVP`; это не разрешение на production/live-подключение.
- **A+B+C+D+E полностью** → можно **запросить** `OPS_OPERATIONAL_ACCEPTANCE` у координатора; объявлять этап завершённым только после явного решения, зафиксированного в GitHub.
- При любом незакрытом пункте: `BLOCKED` / `WAITING_EVIDENCE`, в итоговом отчёте назвать конкретный барьер. Глобальный release всего «Нейрозавода», HANDOFF, платные модели и publisher остаются отдельными заблокированными воротами.
