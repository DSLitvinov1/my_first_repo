# НЕЙРОЗАВОД — внешний свидетель: подготовка и реальные блокировки

Дата 27.10.2026. **Ниже не утверждается, что внешний сервер существует или подключён.** Это инструкция для отдельного администратора инфраструктуры и независимого ревизора по новым исходникам [PR №66](https://github.com/DSLitvinov1/my_first_repo/pull/66).

## Новый источник для отдельного Linux-сервера

- `external_highwater_store.py`: оператор отдельно подготавливает пустую SQLite-БД на защищённом томе только собственного Linux service UID; файл и каталог должны иметь режим без группового/общего доступа. Сервис атомарно и синхронно с диском резервирует **строго следующий** epoch и operation SHA, повтор или пропуск блокируется; при исчезновении ответа состояние считается UNKNOWN, повтор автоматически запрещён.
- `external_highwater_mtls_server.py`: TLS 1.3 серверный приёмник с обязательным клиентским сертификатом от закреплённого CA плюс сравнением DER SHA-256 сертификата конкретного разрешённого клиента. Не имеет команды генерации ключей, создания аккаунтов, копирования ключей из GitHub или слушателя «по умолчанию».
- `remote_highwater_client.py`: Windows-кандидат на однократный TLS 1.3 клиентский запрос с pin проверкой CA, FQDN, DER SHA-256 сервера, отдельной подписанной Ed25519 квитанцией и точными machine/package/source/operation/nonce. Запрещён localhost/link-local для настоящей проверки; сеть/тайм-аут/потеря ответа — UNKNOWN_NO_AUTO_RETRY.
- `independent_witness_receipt.py`: отдельная от TLS-сертификата Ed25519 подпись после фиксации epoch, TTL, строгие параметры, bounded JSON с отказом на дублирование полей.
- Сервер при запуске получает **от другого администратора, не от сети, CORE, Qwen или UI**: server TLS-cert/private key, CA для клиентов, client DER SHA256, собственный Ed25519 signer (желательно HSM/KMS без экспорта), package SHA256, source SHA40, pinned machine SHA256, service user и путь к независимому состоянию.

## Что должен дать уполномоченный владелец, а не разработчик/CI

- РЕАЛЬНЫЙ отдельный Linux-хост с независимым диском/бэкапом и непересекающейся администраторской учётной записью, адрес/домен, отдельный service UID и сеть с закрытым доступом только от будущей машины НЕЙРОЗАВОДА.
- Независимое наименование свидетеля, PIN TLS серверного сертификата, PIN клиентского сертификата, CA, Ed25519 verification key, надёжно защищённую Ed25519 private custody, owner/reviewer/host signer public roots и уровень независимого floor/epoch.
- Подписанный вывод независимого ревизора на точный кандидат, публикацию и отозванные ключи, процедуру невозможности rollback remote-диска (в идеале внешний WORM/HSM).
- Подтверждение владельца для настоящих исходящих сетевых запросов и **одного тестового ограниченного эффекта**.

## Безопасная последовательность

1. Независимый администратор развертывает внешний сервер/том/пользователя, записывает protected trust roots вне репозитория и проверяет mTLS, системное время, ACL, оригинальный SSH/OpenSSL/TLS стек, журнал аудита и резервные копии.
2. Независимый ревизор проводит подмену remote ACK, rollback epoch, отключение сети, rollback Windows/remote state, потерю ACK после durable reservation, проверяет, что всё завершилось UNKNOWN/NO_RETRY и никакой HOST эффект не повторился.
3. Только после этого подписанный издателем установщик с точным digest подключает Windows клиент к заранее одобренному адресу, принимает **свежую** подписанную квитанцию с тем же nonce/operation_id и отдельно контролирует реальный owner-approved protected SCM execution.
4. Подлинное разрешение требует и отдельных signing authorities, и независимого вердикта Issue №11: один успех CI, один hash chain на Windows или сертификат localhost сами по себе **не создают production authority**.
