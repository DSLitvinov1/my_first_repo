# НЕЙРОЗАВОД — первый доказанный отдельный Windows-процесс UI → защищённый Named Pipe → CORE → UI

Дата: 20 октября 2026. База: [DRAFT PR №50](https://github.com/DSLitvinov1/my_first_repo/pull/50), `285e2305cfe8827b91d960164a3ed07d3a339036`. Рабочая ветка `neurofactory-onepc-real-multiprocess-ipc-20261020`.

## Исправлена подтверждённая причина системного E_INVALIDARG

Серия предшествующих испытаний `CreateProcessWithLogonW` / `CreateProcessWithTokenW` ошибочно передавала полное Ed25519-подписанное разрешение Base64 как параметр командной строки. Официальная документация Microsoft ([CreateProcessWithLogonW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createprocesswithlogonw)) устанавливает **лимит 1024 символа** для `lpCommandLine`. Исходный запрос мог превышать лимит; получение `E_INVALIDARG` больше не является свидетельством невозможности создания отдельных Windows-процессов. Попытка поменять только флаги без изменения размера аргументов закономерно не решила проблему.

Исправление использует ТОЧНО существующую ранее проверенную SCM-команду `CreateProcessWithLogonW` из `trusted_host/test_windows_scm_two_user_recovery.py`: локальный домен `.`, `NULL` environment (не наследует секретов GitHub runner), `CREATE_NO_WINDOW`, фиксированный путь Python. Теперь в аргументах — **только короткие имя защищённого канала и путь** к одноразовому заранее подписанному JSON в `%PROGRAMDATA%/nf-core-admission-ci-<random>/signed-owner-permit.json`; длина реальной строки **проверяется условием менее 1024 символов**.

Подписанный текст хранится в отдельном каталоге NTFS, владелец которого и разрешения файла/каталога настроены только на два конкретных Windows SID: подписи/приёмника (изначальный тестовый оператор) и отдельного клиента (только чтение). Другие группы и все унаследованные разрешения удалены, список реальных ACE проверен. В файле нет приватного ключа подписанта или HOST-токена. Дочерний процесс не получает через командную строку или окружение пароли, приватные ключи, GitHub-токены, доступ к базам или право на HOST-эффект. После теста каталог удаляется.

## Что действительно подтверждено Windows

Новый отдельный клиент — **настоящий другой процесс с другим первичным Windows-токеном пользователя**, запущенный через Win32, НЕ только `ImpersonateLoggedOnUser` в основном процессе. Дочерний Python сам проверяет свой `OpenProcessToken(TokenUser)` SID. Он также от собственного Windows-токена пытается прочитать:

- зашифрованный приватный DPAPI-файл подписанта;
- SQLite-базу рабочих черновиков;
- настоящую SQLite-базу CORE.

Все три чтения должны быть отклонены ядром NTFS **до того**, как этот процесс доставит владельцем подписанный запрос. Сервер снова независимо проверяет настоящий SID на Named Pipe с вызовом `ImpersonateNamedPipeClient`, затем существующий `admit_signed_draft` сверяет актуальный черновик, подпись, проект, Git SHA/исходный файл и состояние CORE. Отправитель не вправе создавать новое разрешение, изменять очередь напрямую или выполнять работу.

После завершения ОС-процесса `OneTaskCore` остаётся `QUEUED` в SQLite. **Существующий** `core_readonly_observer` и настоящий HTTP-маршрут `GET /api/core/status` локальной панели успешно считывают этот же результат (`QUEUED` и точные task_id/project_id) и возвращают `execution_allowed=false`, `queue_mutation_allowed=false`, `independently_verified=false`. Исходный пользовательский черновик остаётся `DRAFT_PENDING_OWNER_AUTH`: общий атомарный COMMIT двух SQLite-баз и автоматическая синхронизация состояния **не реализованы**.

## Критически важно: что НЕ подтверждено

**Это ещё не три независимых работающих Windows субъекта.** В успешном сквозном испытании живой UI-клиент имеет собственный отдельный primary Windows SID/процесс; однако контроллер, подписавший офлайн-разрешение, и тестовый приёмник CORE всё ещё выполняются под одним привилегированным SID/процессом тестового координатора. Чтобы безопасно выпускать продукт, надо разместить CORE и приёмник под реальным выделенным Windows SCM Service SID или LocalService с установленным отдельно, только проверяемым публичным ключом владельца и своей NTFS-базой. Контроллер подписи должен остаться изолирован в отдельной Windows-учётной записи, Qwen — без этих полномочий.

CurrentUser DPAPI НЕ является неэкспортируемым аппаратным ключом, не доказывает физическое согласие владельца и не исключает злонамеренный код под тем же SID. Независимый внешний высоководный журнал для полной защиты от отката диска также отсутствует. Нет связанного **в одной установленной версии** полного цикла: живое UI задание → CORE → Qwen → проверенный patch → HOST → восстановление → новая запись об успешном окончании. Отдельные успешные CI-тесты Qwen и установщика не эквивалентны одному полному установленному E2E.

**Установщик оставлен безопасной DRAFT-версией**. Он НЕ получил контроллер подписи, новую службу CORE, полномочия выдачи разрешений или автоматический приём задачи. Это осознанный release gate, а не случайно недоделанная связка.

Не было изменений на пользовательском Windows-компьютере. PR остаётся DRAFT, все предыдущие PR отдельно не объединены, HANDOFF и производство выключены, неподтверждённые SKILLS не активированы. **Независимый REVIEW Issue №11 обязателен до любого merge/installer release.**

## Следующая практическая работа

На одной изолированной Windows-машине испытать **настоящую Windows SCM-службу CORE/приёмника под отдельным SID**, независимый офлайн Windows SID подписи владельца и отдельный Windows SID UI-клиента (всего три разделённых процесса). Перенести существующую проверку разрешения на сервисную сторону; не давать SCM доступ к DPAPI-приватному ключу подписанта, а UI — доступ к CORE SQLite/службе кроме строго защищённой трубы. Подготовить честную `UNKNOWN_NO_AUTO_RETRY` квитанцию, сервисный restart/recovery и проверку отрицательных ACL-сценариев. Только после успешной приёмки этого контракта объединять интеграцию со сценарием одного устанавливаемого Windows-кандидата и реальной Qwen.
