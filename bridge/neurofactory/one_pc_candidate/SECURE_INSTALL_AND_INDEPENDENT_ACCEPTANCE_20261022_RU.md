## 2. Новый закрытый предустановочный контур

`signed_release_staging.py` поддерживает только проверку и КАРАНТИННОЕ КОПИРОВАНИЕ без запуска.

1. Уполномоченный оператор независимо проверяет владельца GitHub, права, точную версию/хэш установщика и три указанных журнала Windows.
2. В отдельном защищённом системном каталоге Windows два разных уполномоченных лица регистрируют **только публичные** Ed25519-ключи владельца и ревизора. Закрытые ключи не помещаются в ChatGPT, GitHub, приложение или SCM. Их выпуск, отзыв, ротация, доверенное хранение пока не реализованы.
3. Оба человека независимо подписывают один и тот же документ: точный commit сборки, SHA-256 установщика, три проверенных run ID, одноразовый nonce, время выдачи и истечения (не более 24 часов). Область подписи ограничена `TWO_PERSON_REVIEWED_INSTALLER_QUARANTINE_COPY_ONLY_NO_EXECUTION`.
4. Под административной учётной записью Windows оператор вручную вызывает модуль проверки. Код не принимает флаги «пропустить ревизора» и не использует публичный ключ из недоверенного сообщения; перед чтением проверяется собственность защищённого каталога и состав реальных NTFS DACL.
5. Если обе независимые подписи, SHA-256, срок и ACL проходят проверку, файл ровно один раз сохраняется в `ProgramData/Neurofactory/Quarantine`, проверяется повторное чтение. Копия **не запускается**, SCM-служба **не регистрируется**, проверенные ключи не становятся рабочей авторизацией.
6. При подмене файла, неверной подписи, недостаточном NTFS-защите, просрочке, повторе или неизвестном состоянии операция останавливается. Самостоятельно удалять карантин и заново подтверждать неизвестный результат нельзя.

Скрипт не создаёт и не подписывает одобрения от реальных людей. CI использует временные синтетические подписи только для тестирования механизма.

## 3. Физическая приёмка на разрешённом Windows-компьютере

Инструмент `physical_windows_acceptance.py` предназначен для отдельного запуска оператором на указанной целевой системе, после того как пользовательская часть законно установлена. Он **ничего не устанавливает и не исправляет**. Проверяет:
- x64 Windows; реальный, не связанный символической ссылкой каталог программы;
- точные 15 исходных компонентов по закреплённым Git blob SHA; не исполняет установленные исходники даже для проверки их подлинности;
- локальную базу SQLite только на чтение, узнаваемую версию схемы;
- наличие, но не содержимое резервных копий;
- отсутствие забытых тестовых SCM-служб на реальном ПК;
- отсутствие автоматической активации и явный статус `BLOCKED_OWNER_OPERATOR_INDEPENDENT_REVIEW`.

Ни один успешный read-only отчёт не превращается в право на выполнение. Отчёт должен оставаться локально, пока оператор не разрешит его безопасную передачу ревизору.

## 4. Обязательные пункты до «полностью готово»

- [ ] Назначен и действительно независимо работает ревизор, он выдал APPROVE/REJECT/INCONCLUSIVE на точном SHA с собственным журналом; Issue #11 остаётся открытым: https://github.com/DSLitvinov1/my_first_repo/issues/11.
- [ ] Согласованы производственные роли Windows, отдельные права и ключи. Нет переиспользования CI-only `NeurofactorySandboxReceiverCI` и `NeurofactoryCoreAdmissionCI` как рабочих служб.
- [ ] Разработан и независимо принят постоянный защищённый SCM-инсталлятор/обновлятор, проверка ключей и принципала, безопасное удаление и восстановление после сбоя. **Сейчас рабочая служба в пользовательский Inno-пакет не включена**.
- [ ] Защищены от отката журнал операций и уже использованные одноразовые разрешения; выбран доверенный внешний witness или документирован эквивалентный риск при работе только на одном ПК. Сейчас независимой защиты от полной замены диска нет.
- [ ] Владелец явно разрешил установку на конкретный компьютер; системный оператор на месте провёл резервную копию и восстановление в пустую папку, сохранив прежние данные.
- [ ] На физическом ПК подтверждён полный непрерывный путь: настоящая локальная Qwen → черновик → подпись владельца → строго отдельная защищённая SCM-служба → подписанная квитанция → устойчивое завершение CORE → без повторного исполнения при аварии; в одном сценарии должны участвовать действительные ключи и действительные права.
- [ ] Проверены ресурсы памяти/диска именно целевого ПК. Облачная Windows с Qwen не подтверждает ресурсы прежнего маломощного резервного компьютера.
- [ ] Владелец подписал окончательный запуск, независимый ревизор APPROVE, контрольные SHA и журналы записаны в доступное ему неизменяемое место.

При отсутствии хотя бы одного пункта: **NO MERGE / NO PROD / NO HANDOFF / NO SKILLS ACTIVATION / NO AUTOMATIC CODE EXECUTION**.

## 5. Текущие внешние ограничения

Для подтверждения «установлено и готово» нужны реально доступный Windows-компьютер с разрешением на изменения, операторские привилегии, раздельные настоящие подписанты и внешний независимый вердикт. Эти факты нельзя заменить GitHub CI или выдуманным одобрением. Никакие логины, пароли, токены и приватные ключи не должны попадать в PR, чат или облачный журнал.
