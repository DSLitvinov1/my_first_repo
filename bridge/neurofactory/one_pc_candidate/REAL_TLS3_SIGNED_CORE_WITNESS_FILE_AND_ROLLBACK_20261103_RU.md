## Почему это ещё НЕ финальное выполнение поручения

Между SQLite CORE, отдельным remote highwater, локальным recipient-intent и NTFS отсутствует совместная атомарная ACID-транзакция. Здесь реализована fail-closed **at-most-once** модель, допускающая `UNKNOWN` и ручное выяснение; она не обещает ровно один эффект при одновременном полном откате самого свидетеля или смене доверенного кода. Нельзя получать право повторно выполнять файл после UNKNOWN из устаревшей локальной базы.

**Невыполненные внешние условия:**
1. Физически отдельный доверенный Linux witness под другим независимым оператором, его реально защищённый, устойчивый к откату монотонный якорь, нетронутые реальные TLS/Ed25519 ключи и доказательство административного разграничения. Доступный `litd12123.clodocd.com` работает под обычным `cloudagent`, `neurofactory-witness` и защищённые файлы на нём не установлены, `sudo -n` не выдан; такой пользователь не вправе самостоятельно объявить себя независимым хранителем.
2. Настоящая постоянно установленная Windows-служба NeurofactoryCoreHost обязана получить защищённую конфигурацию/ключи и в её реальном SCM token использовать новый `OneShotScmRecipientFence` с внешним сетевым TLS ACK **перед** операцией. Старый Windows SCM тест не делает этого общего шага. Windows владелец при последней проверке дистанционно offline.
3. Реальный издательский Code Signing сертификат с контролем личного ключа, подписанный **именно окончательный** проверенный Inno EXE, проверенная цепочка Windows Authenticode `Valid`, точный бинарный SHA256 и публичные пины издателя. Self-signed disposable ключ не подходит.
4. Отдельное подтверждённое независимое человеческое заключение на exact source+installer SHA, реальное NTFS/SCM, реальную удалённую независимость, reboot/restore и отрицательные тесты — [REVIEW #11](https://github.com/DSLitvinov1/my_first_repo/issues/11). Автогенерация APPROVE недопустима.
