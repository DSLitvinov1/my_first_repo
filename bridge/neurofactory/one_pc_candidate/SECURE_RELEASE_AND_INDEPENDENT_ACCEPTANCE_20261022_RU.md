## 2. Границы нового контроля

1. Три действительно отдельно выданных подписи Ed25519: владелец, **независимый** ревизор и независимый внешний свидетель состояния. Каждая связывает один точный выпуск и использует собственное доменное обозначение. Дублирующие ключи и тождественные участники отклоняются.
2. Подписываются: SHA-40 проверяемого коммита, SHA-256 установщика и манифеста компонентов, SHA-256 независимого заключения, проверяемая машина, отдельный свидетель, минимальная эпоха антиотката, ограниченная область разрешения, короткий срок действия.
3. Все сравниваемые «ожидаемые» значения и публичные ключи должен выдавать отдельно защищённый операторский канал; нельзя брать их из UI, предложения Qwen, GitHub-комментария, файла, выбранного самим агентом, или подменять ключами из входящего пакета.
4. Windows Authenticode должен сообщить `Valid`, сертификат издателя совпасть с **заранее независимо зарегистрированным** отпечатком, EXE иметь точно ожидаемый SHA-256 до и после проверки. Нынешний установщик это требование **не проходит**.
5. Даже три технически правильные подписи — это только криптографическая сверка, **НЕ** доказательство реального физического независимого свидетеля, авторизации текущего владельца, подтверждённого устройства, настройки Windows SCM, неподменяемого журналирования и разрешения включить исполнение.
6. Модуль всегда возвращает `release_authorized=false`, `service_install_allowed=false`. Раздельные Windows-операторские процедуры и физическая приёмка ещё не реализованы. Любой неточный/неполный/неверный набор должен быть отвергнут, а не «одобрен по умолчанию».

## 3. Независимая приёмка: обязательный практический порядок

*Этап А — до установки.* Ревизор из [Issue #11](https://github.com/DSLitvinov1/my_first_repo/issues/11) независимо проверяет **точный HEAD нового защищённого кандидата**, изменения и уже пройденные адресные испытания. Он должен собственноручно записать `APPROVE`, `REJECT` или `INCONCLUSIVE`, точный SHA, отдельное доказательство и подписанное заключение. Чужие старые «зелёные» проверки не являются разрешением на этот HEAD.

*Этап Б — независимые доверенные данные.* Владелец/оператор отдельно подтверждают GitHub identity, право на конкретный репозиторий, конкретный Windows-компьютер, принадлежащие разным субъектам ключи Ed25519 и сертификат издателя. Ключи нельзя создавать внутри программы без аппаратного/ОС-порядка хранения; запрет передавать private keys, recovery phrases и пароли в GitHub и чат. Нужен второй независимо администрируемый witness, с сохраняемым вне откатываемого диска монотонным номером; SQLite на том же ПК witness не заменяет.

*Этап В — отдельная доверенная установка.* Администратор проверяет подписанный пакет и резервную копию, устанавливает Windows-службу только из неизменяемого защищённого пакета, проверяет действительные Windows service SID и ограниченный токен, защищённые ACL и невозможность доступа от обычного пользователя/модели, регистрирует и отдельно проверяет доверенные публичные ключи. **Нельзя** просто переименовать текущую `NeurofactoryCoreAdmissionCI` и использовать CI-флаги в производственной установке. Текущий per-user Inno installer не устанавливает защищённую службу — менять это молча нельзя.

*Этап Г — физическая проверка.* На **конкретном авторизованном компьютере** необходимо провести одно безвредное утверждённое задание по непрерывному пути UI → настоящая Qwen → owner-approved CORE → защищённая постоянно работающая HOST-служба → подписанный результат → резервирование свидетелем → долговечный контроль CORE после настоящего перезапуска. Обязательно: чужой пользователь, поддельная подпись, подмена установленного файла/коммита, потеря ACK/UNKNOWN, аварийный рестарт/откат, повторный запуск, восстановление базы и отмена/ротация ключа.
