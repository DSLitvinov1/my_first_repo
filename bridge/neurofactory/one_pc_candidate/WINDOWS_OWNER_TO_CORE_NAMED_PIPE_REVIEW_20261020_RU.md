## Реализовано в уже существующей архитектуре

Новый адресный Windows-модуль `windows_core_admission_pipe.py` повторно использует **существующий TRUSTED HOST** `windows_named_pipe_pilot_receiver.py` — создание защищённого Windows Named Pipe с явной DACL и проверку токена реального подключившегося пользователя через `ImpersonateNamedPipeClient`. Новой очереди и параллельного CORE нет.

Полученный подписанный пакет проверяется не через браузер, а штатным `signed_owner_admission.admit_signed_draft()`, который заново читает реальную локальную SQLite-базу черновиков, проверяет закреплённый вне HTTP публичный ключ владельца, точные SHA-коммита Git, проект, модель, содержимое задания, срок, одноразовость и применяет существующий `OneTaskCore.enqueue()` в **реальную CORE SQLite**. До получения подтверждения от доверенной стороны браузер остаётся только читателем, а исходное задание — черновиком.

Сетевой API, произвольные пути, подписывающие операции в UI, доступ к PRIVATE DPAPI ключу со стороны Qwen, модельная генерация файлов, запуск HOST SCM и производственное выполнение **не добавлены**.

Отправитель дополнительно сверяет **SID процесса именованного Windows-сервера**, а сам сервер сверяет SID фактического клиента после `ReadFile`; имя канала ограничено, первая инстанция зарезервирована, пакет JSON ограничен 8192 байтами, дубли полей и непредусмотренные поля отклоняются. Доверенный SID и публичный ключ берутся из конфигурации вызвавшего тестового контроллера, не из пакета или модели. Подпись Ed25519 не переносится в model prompt как право на выполнение.

## Ограничения, без устранения которых нельзя считать программу готовой

**Тестируемый подписант и CORE-получатель находятся под одним Windows SID в одном одноразовом GitHub runner; это ещё НЕ реальное разделение двух привилегированных учётных записей.** Наличие второго отдельного UI SID и успешный отказ этому пользователю не доказывают защищённость после запуска CORE под иным service account. Необходим отдельный реальный Windows SCM Service SID для CORE, отдельно защищённый signer SID и корректное независимое назначение прав IPC/файловой системы.

Для эксплуатации не хватает **самостоятельно закреплённого вне модели и UI корня доверия**, защищённого хранения OWNER публичного ключа, независимого механизма подтверждения полномочий через GitHub и оператора, антироллбэк свидетеля, надёжного восстановления/отключения при неизвестном результате и полного сквозного installed-app испытания на одной изолированной Windows машине.

Ни этот модуль, ни CLI владельца **не включены в инсталлятор пользовательского UI** и не становятся активными по умолчанию; это намеренная защита от объединения уровня привилегий.
