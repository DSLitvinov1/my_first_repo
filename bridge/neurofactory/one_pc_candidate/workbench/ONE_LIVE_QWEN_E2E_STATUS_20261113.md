## Реальный Qwen (не mock)

На подконтрольном Linux `litd12123.clodocd.com` найден существующий файл модели Qwen 3.5 9B Q4_K_M, ~5.3 ГБ и предустановленный llama.cpp. Модель запущена для испытаний через llama-server на `127.0.0.1:11435` с ключом из отдельного файла режима 0600, с запретом публичного порта и режимом `--reasoning off`.

Адаптер `llama_connector_one.py` проверяет владельца, права и формат файла ключа; обращается только к 127.0.0.1:11435; передаёт структурированный запрос в /v1/chat/completions без передачи содержимого в логи/SQLite; ни один ответ не запускает инструменты напрямую. `work_server.py` поддерживает `--qwen-llama-key-file`, при этом запрещает одновременно выбирать двух локальных провайдеров.

**Реальный тест модели**: в первоначальной конфигурации режим длинного рассуждения дал `UNKNOWN_NO_RETRY` спустя 102,4 секунды; недопустимый план был отклонён. После включения non-thinking и ограниченного JSON-вывода — `PROPOSED` за 20,27 секунды: 3 шага (открыть, проверить текст, снимок). Это был новый тестовый запуск без автоматического повторения прежнего идентификатора.

**Проверка сервера Work**: Work ONE поднят на локальном loopback-тестовом HTTP, токен владельца получен без вывода в логи; `/api/toolmesh/status` подтвердил `qwen.configured=true`, desktop по умолчанию выключен, Google и Bitrix24 не подключены. После проверки пробный HTTP-сервер остановлен.

## Блокировки для полноценного внешнего E2E

1. **Google:** отдельный Google Cloud Desktop OAuth Client ID и согласие пользователя на конкретный тестовый аккаунт. Передавать токены существующего ChatGPT-коннектора в Work ONE нельзя.
2. **Bitrix24:** URL именно тестового портала и его собственное OAuth-приложение/токен со scope `task`, при чтении CRM — отдельный scope `crm`. Рабочие порталы Олега и других клиентов не использовать без отдельного разрешения.
3. **Windows:** установленный локальный Work ONE текущей сборки на выбранном Windows-компьютере отсутствует; физическая приёмка на Windows и CORE9/HOST не проведены.
4. Сервис модели занимает существенную память и CPU. Нельзя без дополнительного ресурсного аудита делать systemd auto-restart и оставлять его как production.
