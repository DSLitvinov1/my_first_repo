# НЕЙРОЗАВОД — защищённая передача подписанного допуска в CORE по Windows Named Pipe (кандидат)

**Дата:** 20.10.2026. **Предыдущая контрольная точка:** PR №48, `5d2d987e402c5d12a79d541e9fda7d8207877443`. Новая отдельная ветка: `neurofactory-onepc-trusted-core-admission-ipc-20261020`.

## Назначение

Подключить уже существующие Windows-контроллер владельца из PR №48, строго проверяемые подписанные разрешения из PR №43, защищённый приёмник Windows Named Pipe из TRUSTED HOST и **настоящую** SQLite-очередь CORE — без создания новой очереди, HTTP API или предоставления браузеру секретных ключей.

Создан `windows_core_admission_ipc_ci.py`. Этот модуль **жёстко ограничен одноразовой Windows GitHub-hosted CI**. Он не устанавливает службу на компьютер пользователя и не предоставляет производственных прав. Скрипт использует уже проверенную реализацию `windows_named_pipe_pilot_receiver._peer_matches` для настоящего вызова ядра Windows `ImpersonateNamedPipeClient` и проверки Windows SID отправителя **после ReadFile и до разбора данных сообщения**.

Локальная труба имеет случайное имя с фиксированным префиксом, DACL без Everyone/Anonymous, допускающим лишь закреплённые SID отправителя и приёмника, и флаг `PIPE_REJECT_REMOTE_CLIENTS`. Пакет ограничен 8192 байтами и точно двумя ключами: schema и уже подписанный permit. Отправитель не может передавать путь к базе, открытый ключ, имя модели в качестве разрешения или право на исполнение.

Приёмник должен получать закреплённый публичный ключ владельца **из независимого доверенного источника, НЕ из сообщения IPC**; затем вызывает существующий `admit_signed_draft`, повторно читающий живой черновик из SQLite, проверяющий подпись, проект, модель, исходный Git-коммит, SHA и срок, а затем выполняющий единственную штатную транзакцию `OneTaskCore.enqueue`. Повторное сообщение отвергается уже существующей схемой singleton. Ответ — **только наблюдение**, не аттестация и не разрешение на claim/HOST effect. При любой ошибке/неизвестном результате повторная доставка автоматически запрещена.

## Адресные проверки

В Windows CI создаются **две реальные временные учётные записи/идентичности** (оператор-подписант и отдельный тестовый пользователь интерфейса). Передача по трубе вызывается из потока с действующим Windows impersonation-токеном другой учётной записи. Ядро Windows подтверждает отправителя, а его попытки напрямую прочитать отдельную защищённую SQLite-базу CORE, SQLite-базу черновиков и зашифрованный ключ DPAPI отклоняются NTFS. Проверяются позитивный одноразовый подписанный enqueue, повторная доставка, чужой/неверный SID, поддельная или просроченная подпись, чужой проект, изменение сохранённого черновика и подмена имени трубы, неверный независимо закреплённый публичный ключ, дублированные JSON-ключи, переполнение размеров и запрет запуска модуля вне разрешённой CI.

**Предыдущая CI-проверка:** [№39346710463](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39346710463), успешно на коммите `9bf137d6d975dce193390912f3f413961aca1bff` (включала 5 адресных + импортированные повторные 7 тестов, в итоге 12). Последующая ревизия намеренно исключает повторный запуск импортированных классов; новые независимые тесты проверяются отдельно. Итоговые результаты последней ревизии нужно сверить по конкретному run/SHA, не использовать старый отчёт как доказательство нового исполняемого кода.

## Что ещё запрещает релиз

1. CI исполняет приёмник и отправитель в **одном процессе, но с проверенным другим Windows impersonation-токеном**. Это подтверждает OS SID/DACL границу, но **не** является испытанием трёх независимых служб или трёх отдельных процессов со своими ограниченными токенами.
2. CI подписант и доверенный получатель используют одну учётную запись тестового владельца. В реальном приложении безопасность требует независимого контроля ключа, выделенного Windows Service SID/учётной записи CORE, закреплённого публичного ключа и проверки права IPC при каждом запуске.
3. Windows CurrentUser DPAPI не защищает от злоумышленного кода, выполняющегося под тем же SID подписанта. Физическое присутствие владельца и неэкспортируемое аппаратное хранение не подтверждены.
4. Нет независимого антиоткатного доверенного свидетеля. Повторные/неясно завершившиеся внешние действия остаются `UNKNOWN_NO_AUTO_RETRY` до ручного решения.
5. Подписанный допуск разрешает лишь **учебную запись в очередь**, не запуск модели, изменение файлов, самостоятельный merge, HANDOFF или публикацию.
6. Реальная Qwen/обработчик предложений, существующий UI и Windows installer пока **не проходят новую единую сквозную установленную интеграцию**. Старые успешные испытания соответствующих компонентов сохраняют силу лишь для неизменённых контрактов.
7. Нет независимого REVIEW №11 и допуска владельца к установке реальной службы. Этот модуль не входит в пользовательский установщик, `live_execution_allowed=False`.

**Режим:** DRAFT, NO MERGE, NO LIVE, NO HANDOFF, NO SKILLS ACTIVATED, NO USER-PC INSTALL.

**Следующий критический этап:** построить защищённый настоящий Windows процесс/Service SID приёмника, отдельный аккаунт подписанта и отдельный аккаунт UI, пройти негативные испытания Windows IPC между настоящими процессами, проверить журнал состояния после аварий, затем связать установленное приложение и пройти независимую приёмку. Без этих пунктов полноценный Windows-НЕЙРОЗАВОД ещё не завершён.
