# НЕЙРОЗАВОД — трёхсторонняя Windows SCM интеграция: что подтверждено, почему выпуск заблокирован

Дата проверки: 20.10.2026. Stacked-base: [DRAFT PR #52](https://github.com/DSLitvinov1/my_first_repo/pull/52), `14a93fc26508e7df8bb1b794c8514103d89c635c`. Эта ветка `neurofactory-onepc-triple-sid-scm-core-admission-20261020`.

## Реальный код в новой ветке

1. `windows_scm_core_admission_ci.py`: отдельная фактически установленная **на одноразовую Windows-2025 GitHub-hosted CI-машину** Windows-служба `NeurofactoryCoreAdmissionCI` под `NT AUTHORITY\LocalService` и **ограниченным собственным per-service SID** `S-1-5-80-...`. Получает только закреплённый публичный Ed25519 ключ оператора из защищённой конфигурации. Не получает приватного DPAPI-ключа, не принимает от клиента внешние пути/права, не исполняет модель и не включает HOST.
2. Защищённый Named Pipe использует существующий `TRUSTED HOST.windows_named_pipe_pilot_receiver._peer_matches` с `ImpersonateNamedPipeClient`, отдельный реальный SID клиента из операторского файла конфигурации. При успешном допуске вызвал бы неизменённый `signed_owner_admission.admit_signed_draft` и `OneTaskCore.enqueue`. Любой отказ фиксируется `DENIED_OR_UNKNOWN_NO_AUTO_RETRY`, без обхода проверки Git-коммита и без следующего запуска очереди.
3. `test_windows_scm_core_admission_ci.py`: создаёт одноразовую третью локальную Windows-учётную запись UI и защищённый CurrentUser-DPAPI ключ оператора, копирует уже существующие исходники/SQLite в отдельные ACL-каталоги ProgramData, регистрирует и затем удаляет только тестовую SCM-службу. Проверяет, что собственный SID службы, отдельный SID владельца и SID UI различны. Реальный клиент передаёт уже подписанный документ из отдельного процесса через Named Pipe; его права на прямое чтение ключа, workspace SQLite и CORE SQLite должны быть запрещены. Не применяется к компьютеру пользователя.
4. Путь Git и SHA-256 установленного `git.exe` дополнительно закреплены отдельно от сообщений IPC. Ни пароль, ни GitHub-токен, ни приватный ключ в конфигурацию службы не записаны.

## Что подтверждено и что НЕ ПРОШЛО

**Проверено по фактическому журналу Windows CI:** SCM действительно создаёт службу с `LocalService` и ограниченным service SID; прежний этап в работающем процессе подтверждал запрет доступа другой учётной записи к DPAPI-ключу. Приём и проверка Ed25519 владельца и настоящий одноразовый enqueue из предыдущего **двухпроцессного** PR №52 прошли на точном коммите `14a5402aad7079a5940609a1938cb4329add595e`, Actions [№39349885697](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39349885697).

**НО НОВЫЙ ТРЁХПРОЦЕССНЫЙ E2E НЕ ПРОШЁЛ.** Это настоящая блокировка безопасности/совместимости SCM. Последовательно обнаружено:

- Действующая защищённая SCM-служба принимала запрос, но неизменённый CORE отвергал источник: `CoreSafetyError: Source commit not verifiable in local Git object store`. Отказ честно отражался как `DENIED_OR_UNKNOWN_NO_AUTO_RETRY`; очередь не была подтверждена как QUEUED. Существовавшая тогда проверка подписанта не имела доступа к закрытому DPAPI-файлу.
- Для решения исключён неявный runner PATH: запуск `git.exe` привязан к фиксированному установленному администратором Program Files Git и его точному SHA-256, подготовлены Service-SID каталоги TMP/HOME, проверяются только разрешённые Git-источники, обязательная проверка точного commit SHA не отключена.
- Системный код дочернего Git из ограниченной SCM-службы **3221225794 = 0xC0000142 (STATUS_DLL_INIT_FAILED)**, без stderr. Это ошибка инициализации DLL подпроцесса Windows; нельзя объявлять причиной исключительно отсутствие PATH или происхождение Git-объекта. Самый поздний [Windows Actions №39440519567](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39440519567) на коммите `807b27e4a7eec0c973b26e49a30e0115000bed6f` **FAIL** с этим кодом. Он должен оставаться красным — не пропускать Git source check, не ослаблять restricted SID и не выдавать CI тест за пройденный.
- По публичной документации Microsoft DLL-инициализация может сбоить из-за прав доступа к window station/desktop и других условий среды служб; **точная причина именно этого экземпляра ещё не подтверждена**. Нужна диагностика restricted-service child process / DLL / console / Event Log в отдельной разрешённой Windows среде; также проверьте доверенный отдельный Git binary или независимо проверенный источник Git при СОХРАНЕНИИ запрета самовольного изменения базового коммита.

Итог: положительные доказательства перехода UI → CORE из PR №52 и реальная Qwen из PR №51 не исчезают, но новые три разные процессы + отдельная SCM CORE с полной проверкой Git ещё не удовлетворяют условиям релиза.

## Не выпускать в производство, пока не закрыты

- Реальная SCM-приёмная служба под отдельным ограниченным SID должна **проверять неизменённый Git SHA без ошибки DLL** и поставить ровно одну подписанную задачу в CORE SQLite. Обязательно отрицательные тесты: чужой UI SID, чужой проект, поддельная подпись, просроченный срок, replay, отсутствие доступа SCM к приватному ключу владельца, отсутствие доступа UI к CORE. В случае неизвестного исхода — ручной разбор, без повтора.
- Требуется отдельное доверенное закрепление публичного ключа владельца и безопасное размещение файлов приложения/службы, настоящая квитанция о полном выполнении и независимая проверка против полного отката диска.
- Требуется ОДИН полный установленный Windows-кандидат (из прежнего установщика, без выдачи UI полномочий): настоящий пользовательский запрос, signed CORE, настоящая локальная Qwen, сохранённое предложение, REVIEW, безопасное восстановление и демонстрация без автоприменения кода.
- Не выполнено независимое одобрение [REVIEW Issue №11](https://github.com/DSLitvinov1/my_first_repo/issues/11); PR №558 SKILLS не объединён и навыки не активированы.
- Компьютер владельца не менялся; локальный пользовательский установщик безопасно остаётся в режиме DRAFT. Ветки PR №43–52 не объединены, производственная очередь, HANDOFF и опасные исполнительные команды выключены.

**Статус: НЕЙРОЗАВОД ПОДГОТОВЛЕН ЧАСТИЧНО, ПРОИЗВОДСТВЕННЫЙ РЕЛИЗ ЗАБЛОКИРОВАН. DRAFT / NO MERGE / NO LIVE / NO INSTALL.**
