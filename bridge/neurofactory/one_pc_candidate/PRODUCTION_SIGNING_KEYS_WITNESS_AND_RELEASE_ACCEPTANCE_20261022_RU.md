# НЕЙРОЗАВОД — выпуск с подписью, ключами и независимым внешним свидетелем

Контрольная точка: 22 октября 2026 года. Это продолжение готовящегося релиза PR №58 → №60 → №61 → №62 → №63. В этом изменении не пересобирались и не корректировались протестированные Qwen, CORE, исполнение Windows HOST, пользовательский UI, SKILLS или SELFDEV.

**Статус:** безопасность выпускного контроля расширена; фактическая подписанная производственная установка всё ещё не выполнена, неподтверждённые ключи не активированы.

## Новые исходники

- `independent_witness_receipt.py` — криптографически связывает подписанное Ed25519 наблюдение внешнего свидетеля с конкретным SOURCE SHA, SHA-256 пакета, SHA-256 отчёта ревизора, идентификатором машины, SHA-256 операции, nonce и монотонной эпохой; запрещает перепутанные подписи, повтор старого номера, истекший срок и подменённое содержимое. Отдельный разбирающий сетевой JSON ограничитель запрещает дубли, NaN, слишком большие входящие сообщения.
- `windows_setup/audit_windows_operator_public_pins.ps1` — **только чтение** уже установленного независимым оператором файла публичных ключей по фиксированному защищённому пути Windows ProgramData. Проверяет владельца папок/файла, отсутствие reparse/junction, отключённое наследование ACL, отсутствие права записи у неподтверждённых SID. Файл и ключи этим скриптом **не создаются**. В случае отсутствия настоящего файла — отказ.
- `combined_release_review_gate.py` — связывает уже существующий независимый трёхсторонний релизный допуск PR №60, сертификат подлинности Windows Authenticode, отпечаток издателя и новые доказательства внешнего highwater, требуя соответствия одной версии/машины/заключения.
- `.github/workflows/neurofactory-onepc-external-witness-gate-ci.yml`, `...windows-public-pins-acl-ci.yml`, `...combined-release-gate-ci.yml` — только адресные тесты новых границ. Тестовые ключи создаются в оперативной памяти исключительно при CI; они не переносятся в production.

Все новые инспекторы **всегда** явно указывают: реальный владелец не аттестован, доказательство физически отдельного внешнего свидетеля отсутствует, production install/автоматическая очередь/выполнение заданий **запрещены**.

## Конкретная последовательность перед настоящим релизом

1. Независимый ревизор проверяет полный точный кандидат, его SHA и результаты всех тестов. Выдаёт отдельное самостоятельно подписанное **APPROVE** с точным SHA исходника/пакета, полномочиями и сроком действия. Пока открыт [Issue №11](https://github.com/DSLitvinov1/my_first_repo/issues/11), подписи ревизора нет.
2. Уполномоченный владелец подтверждает свой GitHub repository ACL и конкретный доверенный Windows ПК; отдельный оператор проверяет live ACL и аппаратную идентичность. Публичные ключи owner/reviewer/operator/witness устанавливаются ОТДЕЛЬНО в защищённый раздел Windows с ограничением записи администраторами; секретные ключи **не публикуются** в GitHub, чате, пакетах или пользовательском UI. Дублирующие участники/общий секрет не допускаются.
3. В отдельном доверенном удостоверяющем или аппаратно защищённом подписывающем контуре регистрируется реальный сертификат **Code Signing** организации/издателя. Собирается установщик из утверждённой версии, подписывается средствами издателя, дополнительно проверяется Windows `Get-AuthenticodeSignature=Valid`, независимый отпечаток сертификата, точные SHA-256/размер/состав бинарников и период действия. Старый unsigned Inno нельзя переименовывать в «production».
4. На реально отдельно администрируемом узле создаётся внешний witness/highwater с независимо защищённым хранилищем монотонной эпохи, mTLS-сертификатом и журналом. Каждое разрешение на эффект/установку должно потребовать **свежий удалённый подписанный ответ**, а не чтение локального файла или старой подписанной квитанции. Сетевой таймаут, неопределённый эффект и подозрение на откат должны приводить к `UNKNOWN / NO AUTOMATIC RETRY`. Текущий модуль только **проверяет предоставленное** доказательство, а не опрашивает такой узел.
5. Подписанный production-инсталлятор привязывает хэш UI-пакета, защищённой SCM-службы, pinned CORE/HOST/Qwen-адаптера и доверенные roots к точной версии, создаёт restricted per-service SID с раздельными ACL на исполнитель/данные/ключи/резервные копии, умеет обновляться и откатываться под независимым наблюдением. Нельзя называть дежурный `NeurofactoryCoreHost` исполнителем: пока он не применяет команды.
6. Приёмка на целевом Windows ПК: реальная Qwen → ручное подписанное owner admission → настоящая постоянно действующая ограниченная CORE/HOST-служба → одно разрешённое инертное действие → внешняя фиксация UNKNOWN/commit → подписанная квитанция → SQLite перезапуск → отсутствие повторного эффекта → восстановление из backup, отзыв/переиздание ключей, защита от запретного обновления и подмены установщика/службы.
7. Только отдельный ревизор после самостоятельной проверки вправе закрыть Issue №11 и подтвердить статус ACCEPTED на окончательный двоичный SHA. Разработчик/CI-автор не может выступать независимым подписантом за владельца.

## Проверка технологии Authenticode для настоящего Inno EXE

Создан отдельный эксперимент `.github/workflows/neurofactory-onepc-disposable-authenticode-signing-ci.yml`: получает точно закреплённый исходный НЕПОДПИСАННЫЙ Inno EXE из ранее собранного тестового артефакта, только на одноразовом hosted Windows генерирует **короткоживущий самоизданный тестовый сертификат**, подписывает тот же EXE средствами Windows SDK, перепроверяет подпись через `Get-AuthenticodeSignature` и уже существующий `windows_package_preflight.py`, требует отказа на **чужом** сертификате и удаляет временные Windows trust-записи. Программа/установщик не запускаются и подписанный тестовый файл **НЕ распространяется** как производственный пакет.

[Проверка этого экспериментального пути #39794844432](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39794844432); точный окончательный статус следует смотреть в Actions. Такая подпись не заменяет реальный сертификат издателя и не разрешает Windows service installation.
