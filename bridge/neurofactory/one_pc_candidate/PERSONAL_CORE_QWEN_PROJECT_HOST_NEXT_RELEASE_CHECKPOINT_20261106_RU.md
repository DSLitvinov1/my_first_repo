## Реально реализовано в новой существующей ветке GitHub

Ветка `neurofactory-personal-core-qwen-host-projectfiles-20261106`, основана на текущем DRAFT PR #101; не новый проект, не merge и не рабочий deploy.

1. **HOST, действие `create_project_file` помимо прежнего `write_note`.** Новый `personal_project_file_effect.py`: единственный CREATE_NEW (без перезаписи) простой исходный файл максимум 2048 UTF-8 байт с точным SHA256, расширения `.py,.js,.ts,.tsx,.md,.txt,.json,.html,.css,.yaml,.yml`, без путей/escape, DOS-устройств, symlink/reparse, команд ОС или автоматического запуска созданного кода. Только внутри ранее отдельно созданной папки `C:\ProgramData\NeurofactoryPersonalHost\projects\<verified-uuid>\`.
2. **Связка реального пользовательского CORE-реестра задач и Qwen.** `personal_core_qwen_file_approval.py` читает существующую `NeurofactoryData/workspace.sqlite3` **mode=ro**, требует реального task/project relation, сохранённого статуса `PROPOSED_UNVERIFIED`, модели `qwen3.5:9b` или `qwen2.5-coder:1.5b`, целостности содержимого. Полный текст показывается владельцу в интерактивной консоли, после введения task-specific подтверждения **перечитывается повторно** и подписывается отдельным доменом `NF_PERSONAL_OWNER_QWEN_PROJECT_FILE_V1`. Разрешение содержит одну точно определённую CORE/Qwen-политику: task/project/model/draft/content SHA, разрешённое имя файла, ограничение байт и один Linux epoch. **Никакой автоматической подписи самим Qwen**.
3. **Существующая реально установленная Windows-служба в обновляемых исходниках** сохраняет ветку прежнего owner-signed `write_note` и добавляет строгое распознавание второго signed schema, разделённый домен Ed25519, проверку CORE/Qwen-полномочий **до локального UNKNOWN**, и только затем существующую цепочку: durable local UNKNOWN → signed remote Linux epoch → после ACK разрешённое CREATE_NEW → проверка SHA файла → durable `EXECUTED`. Повтор или потерянное подтверждение никогда не запускается автоматически.
4. **Изолированная папка проекта:** `Provision-NeurofactoryPersonalProjectFolder.ps1`, одноразовая проверка уже существующего Limited LocalService/Service SID и выделенная папка с ACL SYSTEM/Admin/Service SID Modify/Owner Read. ## Следующий безопасный реальный этап (если Windows администрирование доступно через разрешённый инструмент)

- Сначала сверить действующий SCM и существующий Windows/Linux epoch 1 **без каких-либо сбросов/повторов**. Создать backup действующего Windows runtime, operator config и SQLite. Не трогать реальный Qwen UI и чужие проекты.
- Для нового HOST релиза требуется **одна согласованная миграция pinned source SHA + package SHA одновременно в Windows и физическом Linux**. Только после проверки SHA нового готового bundle/импорта и signed HEAD, без изменения owner private key, remote signer private key, SSH forced-command и содержимого SQLite. Нельзя переносить версию только на Linux: старая запущенная служба fail-closed остановится.

Одно подтверждение, один Linux epoch 2, один реальный `EXECUTED`, один read-back; не запускать созданный код. При UNKNOWN — ручная сверка и отказ от ретраев.
- Полная перезагрузка всей Windows потребует закрытых/сохранённых пользовательских приложений и работающего автозапуска Desktop Commander. После фактической перезагрузки выполнить только целевой `Verify-NeurofactoryAfterWindowsReboot.ps1`. **SCM stop/start — не эквивалент настоящему Windows reboot**.

Не выдавать собственную approval metadata за полноценную очередь CORE.
