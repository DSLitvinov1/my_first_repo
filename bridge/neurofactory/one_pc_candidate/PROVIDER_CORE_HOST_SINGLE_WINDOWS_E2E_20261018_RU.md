## Что реально сделано

Одна одноразовая тестовая Windows-2025 машина, один запуск:

1. Настоящий `OneTaskCore` создаёт Git-исходник, фиксирует одно задание в SQLite и выделяет аренду обычному worker.
2. Перед вызовом модели используется **настоящий** `core.provider_preview(task_id)`, который создаёт неизменяемый пакет `neurofactory.coordination.provider_bridge.v1` с корреляцией SHA-256 входной задачи, отдельными путями CORE и PROVIDERS, точной моделью и всеми флагами разрешений `false`. Фикстура проверяет эти ограничения; подписывается только проверенное соответствие пути HOST, а не непроверенная инструкция модели. Настоящий `PROVIDERS` `ollama_worker.execute_one` делает локальные HTTP GET /tags и POST /generate на **тестовый** Ollama-compatible HTTP-сервер `127.0.0.1:11434`; резервирует попытку в настоящем отдельном `DurableBudget` с fsync.
3. **Ответ модели создан тестовой заглушкой, а не моделью Qwen.** Поэтому `offline_mock=false` внутри старого адаптера описывает видимый HTTP-transport, а НЕ достоверность происхождения модели. Сам интеграционный тест недвусмысленно сообщает `FAKE_MODEL_ONLY`.
4. Контроллер подтверждает, что предложение соответствует строго заданному безвредному тексту и единственному разрешённому пути. До такого одобрения оно остаётся `PROPOSED_UNVERIFIED`.
5. Эфемерный приватный Ed25519 ключ оператора CI подписывает **ровно проверенный байтовый пакет**; ключ не передаётся отдельной SCM-службе и worker.
6. Запущенная средствами Windows SCM ограниченная LocalService служба проверяет реальную подпись, привязку к worker SID и реальную ACL. Создаётся один новый безвредный файл с точным SHA-256, владеет им служба, а не CORE/model.
7. Проверяется readback файла, отказ поддельной подписи, отказ worker на прямое чтение/запись protected_output, отказ повторного пакета и после принудительной остановки/рестарта SCM процесса.
8. Два дополнительных отрицательных теста PROVIDERS: уже зарезервированное task_id не допускает второго запроса генерации; чужой путь в ответе тестовой модели даёт `INVALID_MODEL_OUTPUT` и не получает разрешение на запись.

## Обязательные ограничения

- Не установлен и не проверен пользовательский Windows-компьютер.
- **Qwen не исполнялась в этой интеграции**. Настоящий HTTP провайдер не подтверждает настоящие модельные веса или происхождение ответа.
- На этой ветке нет UI ↔ реальная очередь и полноценного выполнения произвольных задач: исполнитель — только зафиксированный учебный текстовый файл, как требует HOST CI safety.
- Подпись в текущем тесте создана эфемерным ключом CI-оператора, не реальным Windows TPM/CNG владельца. Не существует независимого, вне машины размещённого монотонного журнала. SQLite и журнал одного ПК не защищают от полного отката образа.
- Последовательное событие `claimed` → `PROPOSED_UNVERIFIED` → `owner signed` → `receiver file` проверено тестом. Возврат окончательной квитанции в durable CORE завершённую запись ещё нужно спроектировать и протестировать: текущий настоящий CORE остаётся в состоянии `CLAIMED` после HOST эффекта.
- Процедура независимого REVIEW на точной ревизии отсутствует. Не открывать LIVE, не устанавливать службу на ПК владельца без одобрения, не объединять PR и не активировать HANDOFF.

## Дальнейшие задачи до готового продукта

1. Закрыть доверенный канал получения настоящего разрешения владельца на реальном ПК и durable CORE completion по подписанной HOST квитанции, без слепого повторного выполнения.
2. Провести настоящий Qwen/Ollama probe на одной авторизованной Windows машине после проверки RAM, модели, локального порта и собственной защищённой квитанции PROVIDERS.
3. Подключить реальную read-only телеметрию CORE/OPS к существующему UI, затем строго ограниченное создание задания с серверным ACL и настоящим owner approval.
4. Проверить осмысленное восстановление после краша и перезапуска той же физической машины, резервную копию, восстановление и независимый REVIEW №11.
5. Подготовить установщик с явным подтверждением оператора и разграничением пользователей/SID; до приёмки — только кандидаты и одноразовые тестовые среды.
