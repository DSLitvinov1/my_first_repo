# НЕЙРОЗАВОД — проверенное исправление Windows SCM → Git → CORE. 21.10.2026

## Важнейший результат

Главная подтверждённая блокировка PR №53 (`0xC0000142 STATUS_DLL_INIT_FAILED` при запуске `git.exe` из SCM LocalService с restricted per-service SID) устранена адресным исправлением Windows subprocess **без снятия прав доступа и без пропуска проверки исходного Git-коммита**.

- [Windows CI #39597283729](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39597283729) диагностически подтвердила, что для одного и того же защищённого LocalService SCM и закреплённого `git.exe`: стандартный запуск даёт exit `3221225794`, `CREATE_NO_WINDOW` — exit `0` и корректный 40-символьный HEAD, `DETACHED_PROCESS` — exit `0` и корректный HEAD. Диагностика не принималась за успешный CORE E2E.
- В `bridge/neurofactory/development/core_owned/one_task_core.py` сохранена стандартная проверка `_verify_git_source`: HEAD, `rev-parse --verify ...^{commit}`, ls-tree, `show`, SHA-256. Исправлено только Windows subprocess создание: `CREATE_NO_WINDOW`, `stdin=DEVNULL`; POSIX без изменения режима.
- В `windows_scm_core_admission_ci.py` предшествующий обычному CORE контроль наличия Git SHA проводится с тем же флагом. Запуск всё ещё требует фиксированный vendor-installed Git.exe с операторски закреплённым SHA-256 и restricted SID. Запись в CORE доступна только после реальной подписи Ed25519, совпадения живого SQLite-черновика, Git SHA источника, project/model и полномочия Windows-клиента.
- Исправлены адресные NTFS ACL на **уже существующие** `core/state` и `core/sandbox`: реальная SQLite транзакция требует создание временного журнала рядом с базой. Разрешения сохранены только для отдельной защищённой SCM-сущности/LocalService и доверенных системных владельцев, не для интерфейса или Qwen.
- [Windows CI #39597876102](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39597876102), SHA `4ca3bac06ebd3aad0995c6c165283f5424941970`: **SUCCESS**, одна настоящая защищённая SCM LocalService-служба под отдельным restricted Service SID, отдельная учётная запись DPAPI-подписанта, отдельный реальный Windows OS-процесс UI под третьим SID. Подписанное разрешение доставлено через Named Pipe, существующий CORE создал точно одну SQLite запись `QUEUED`. Доступ к ключу подписанта и базе CORE от UI отклонён; службе приватный DPAPI-ключ недоступен.
- [Windows CI #39598301601](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39598301601), точный SHA `1970d3d2090ea84df1f994cdae78719af63168a2`: **SUCCESS**, аналогичный положительный трёхпроцессный проход плюс **реальная повторная доставка** того же действительного подписанного разрешения другим процессом UI: CORE не принял второе задание, `DENIED_NO_RETRY` и старое единственное задание сохранилось. Один выбранный интеграционный тест, повтор тяжёлых Qwen и Inno не требовался.
