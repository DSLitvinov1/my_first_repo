# НЕЙРОЗАВОД — критический этап приёмки целостности ВСЕЙ программы на Windows

Дата контрольной точки: 27.10.2026. Пользователь разрешил продолжать разработку, начиная с самого критичного. Мы не начали проект заново: ветка разработана на базе DRAFT PR #68 и предыдущих проверенных CORE/HOST/Qwen.

## Обнаруженная критическая слабость

Предыдущий `owner_pc_readonly_acceptance.ps1` подтверждал SHA-256 ровно 15 CORE/HOST/PROVIDERS/COORDINATOR модулей, но только **наличие** файлов local_workspace.py, runtime/python.exe, ui/app.js и других интерфейсных компонентов. Такая проверка не могла обнаружить изменение GUI JavaScript или основного Python веб-сервера после установки. Утверждать, что вся установленная программа проверена, было бы неверно.

## Исправление без регистрации/включения HOST

1. `build_owner_review_package_manifest.py` создаёт во время сборки staging-список SHA-256 **всех** исполняемых, UI, runtime, launcher, компонентных и аудитных файлов, заранее проверяет точные относительные пути, ограничивает размер/количество, исключает ссылки, повторы и неожиданные файлы. Отдельный `package-integrity.json` входит в уже существующий per-user Inno, но НЕ содержит никаких секретов и никогда не разрешает реальные задания.
2. `owner_pc_readonly_acceptance.ps1` теперь требует два **ВНЕШНЕ ПЕРЕДАННЫХ** SHA-256: неизменённого components/manifest.json и нового package-integrity.json. Верифицирует заново каждый из файлов, включая собственный инертный скрипт, и отказывает при любом несовпадении/дополнительном незакреплённом исполняемом файле. Ожидаемый SHA должен сверяться с логом доверенной CI сборки, а не автоматически браться из самого установленного каталога.
3. При частной проверке Ollama скрипт читает только локальный GET `127.0.0.1:11434/api/tags`; ни модель не загружает, ни Qwen текст не исполняет. Нет записи в пользовательские данные, сети наружу, прав администратора, HOST/CORE/подписных полномочий или изменений реальных задач.
4. Новый изолированный Windows workflow исполняет настоящую установку per-user пакета на временной машине, сверяет весь staging hash, намеренно подменяет UI JavaScript и добавляет `app/sidecar.py`: каждое изменение должно быть **DENIED**. Существующие бэкап/RESTORE, SQLite, повторный запуск приложения, uninstall со сохранением пользовательской базы и отказ Production также проверяются повторно.

## Непреодолимые внешние ограничения и честный статус

- **Это GitHub-hosted Windows-раннер, НЕ компьютер владельца.** Remote Desktop Commander до этого показал оставшуюся квоту 0%; подтвердить актуальный self-hosted GitHub Runner и физически установить на Windows владельца через текущие доступные инструменты нельзя. Никаких изменений на ПК не производилось.
- **Тестовый installer не подписан издательским Authenticode**, а отдельная проверка manifest SHA только после установки не аутентифицирует сам скачанный файл; проверка собственной целостности из локально установленного скрипта тоже НЕ защищает от изменения самого проверяющего скрипта высокопривилегированным атакующим. Для production необходим доверенный исходный канал, реальный издательский сертификат и независимый ревизор финального SHA.
- Пакет содержит безопасный UI/SQLite и inert source CORE/HOST, но **не включает** фактическую постоянно установленную защищённую HOST службу и реальное выполнение разрешённых задач. Подтверждённый ранее настоящий Qwen→CORE→restricted SCM→local signed журнал/перезапуск [№40542374090](https://github.com/DSLitvinov1/my_first_repo/actions/runs/40542374090) существует только в disposable Windows CI.
- Отдельный внешний witness не нужен для локальных черновиков и предварительной read-only приёмки, но необходим для полной антиоткатной модели, если независимый reviewer требует её для production; не подменять его локальным SQLite.
- **Независимый подписанный вердикт Issue #11 отсутствует.** Ветки остаются DRAFT, без слияния в main и запуска живых задач/способностей SKILLS. На физической машине безопаснее испытывать только изолированную виртуальную Windows после сверки EXE SHA и отдельного доверия к источнику.

Остались реальные критические условия для полного результата: доверенный Windows-канал и состояние пользователя/архитектуры, настоящий код-сайн сертификат, назначенный независимый ревизор, реальная установка/перезагрузка и подтверждённый binding защищённой SCM службы к CORE. Не заявлять успешную физическую приёмку до исполнения.
