# НЕЙРОЗАВОД — завершённое лабораторное сквозное испытание Qwen → CORE → защищённый SCM HOST

Дата: 22 октября 2026 года. **Только одноразовая Windows-2025 виртуальная машина GitHub-hosted. Производственная установка НЕ выполнена.**

## Достигнутый новый результат

Один непрерывный контролируемый сценарий использует **настоящие веса Qwen через настоящий Ollama**, установленную локальную пользовательскую программу, действительную SQLite-базу черновиков, отдельное разрешение владельца с Ed25519 и подлинную изолированную Windows SCM-службу под `NT AUTHORITY\LocalService`, имеющую выделенный **RESTRICTED per-service SID**. Отдельный пользовательский процесс передаёт одно безвредное разрешённое действие HOST; защищённый HOST подписывает результат, CORE сверяет квитанцию и записывает долговечный `HOST_CHECKPOINTED_TEST`.

Никаких новых заглушек для Qwen: на первом этапе запущено реальное локальное модельное inference. Безопасный тестовый HOST записывает **только отпечаток уже сохранённого предложения**, а не выполняет/устанавливает модельный код. Следовательно, это доказательство интеграции границ Qwen/CORE/HOST, а НЕ самостоятельной способности агента изменять произвольные файлы проекта.

## Непрерывный тест и доказательства

- Тест: `bridge/neurofactory/one_pc_candidate/test_real_qwen_actual_restricted_scm_ci.py`. Происходит непосредственно в том же одноразовом Windows-раннере, который установил пользовательский Inno-кандидат и получил настоящие веса Qwen. Использована подтверждённая копия SQLite с одной черновой задачей и одним предложением.
- Настоящий подписанный owner admission использует `signed_owner_admission.admit_signed_draft`, а не `enqueue(...lambda True)`; поддельный owner signer отклоняется до постановки. Только после него реальный CORE атомарно принимает и резервирует ровно одну работу.
- Отдельное доменно-разделённое разрешение владельца связывает точный SHA файла и содержимое отчёта об исходном Qwen-предложении. Проверки Host peer Windows SID и service SID используют системные API, а не фиктивные строки учётных записей.
- Реальная отдельная SCM-служба HOST выполняет одно безвредное создание тестового файла, пишет подписанную квитанцию; реальный CORE подтверждает, долговечно закрывает и повторно открывает SQLite. Повторная подача подписи/квитанции и аварийный перезапуск службы **не создают второй эффект**.
- Снимок реальной SQLite/Qwen остаётся черновиком `DRAFT_PENDING_OWNER_AUTH` и не помечается автоматически `APPROVED`; текст Qwen не выполняется и не может изменить исходные файлы.
- Итоговый workflow: `.github/workflows/neurofactory-onepc-real-qwen-restricted-scm-same-run.yml`.
- **Точный прошедший кодовый SHA:** `1938ff65a81ff20f4dd75656c3f5d6d5f6a5cb6d`.
- **Единственный новый workflow:** https://github.com/DSLitvinov1/my_first_repo/actions/runs/39762142770 — PASS, включая оба настоящих программных компонента на **одном** Windows-hosted раннере. Старые Qwen/SCM тесты на отдельных ветках не перезапускались.
- В журнале: `NF_GENUINE_QWEN_SQLITE_TO_OWNER_SIGNED_CORE_AND_REAL_SCM_HOST=PASS_CI_ONLY`, `NF_ONEPC_CORE_SQLITE_HOST_COMPLETION=HOST_CHECKPOINTED_TEST`, `NF_WINDOWS_SCM_CRASH_RESTART_NO_REPLAY=PASS_TEST_ONLY`, `NF_GENUINE_MODEL_TEXT_NEVER_EXECUTED_ONLY_FINGERPRINT_RECEIPT=PASS`.
