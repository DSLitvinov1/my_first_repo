# НЕЙРОЗАВОД — защищённая Windows-служба: контрольная точка готовности к приёмке

Дата: 22 октября 2026 года. Это прямое продолжение объединённого PR №58 и защищённого выпуска PR №60, **не отдельный новый проект**.

## Реально реализовано

1. Реальная отдельная Windows-служба `NeurofactoryCoreHost` с собственным обработчиком Windows Service Control Manager и ручным типом запуска (`DEMAND_START`). Служба запускается из Python 3.12.10 с проверенной контрольной суммой, работает под `NT AUTHORITY\LocalService` и реальным выделенным `SERVICE_SID_TYPE_RESTRICTED`, умеет корректно останавливаться и запускаться вновь. Привилегированная регистрация показана **только на одноразовом Windows GitHub-hosted раннере**, не на ПК владельца.
2. Жёсткое разделение NTFS ACL: только администраторы/SYSTEM управляют исполняемыми файлами и конфигурацией, служба не может записывать в корень установки, выделенный service SID может записывать только диагностический файл в `status/`; обычный LocalService не получает право записи туда. Настоящая ограниченная служба подтверждает отказ записи в корень.
3. Отдельная неактивная конфигурация. Любая попытка установить `core_queue_allowed=true`, `real_host_execution_allowed=true`, разрешить публикацию/сеть/внешнего свидетеля через фальсификацию конфигурации отклоняется. Отдельно проверены реальная остановка службы, подмена настройки с отказом запуска и безопасный повторный запуск после восстановления настроек оператором.
4. Отдельный только читающий `audit_protected_host_readonly.ps1`: собирает факты фактической Windows-службы/области прав/файлов/учётной записи и всегда возвращает `DORMANT_RESTRICTED_SCM_OBSERVED_NOT_RELEASED`. Не меняет ОС, не выдаёт право на исполнение.
5. Доставляемый оператору защищённый контейнер `Neurofactory-Protected-Host-Operator-Review-UNSIGNED.zip`, доступен как артефакт из [облачной сборки №39758320407](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39758320407). Внутри: 39 контролируемых исходников и файлов Runtime, защищённая конфигурация с отключёнными действиями, отдельный скрипт read-only аудита и инструкция. **Архив не является подписанным исполняемым установщиком и не устанавливается автоматически.**

## Границы, которые нельзя маскировать

- Новый Windows SCM — **дежурный ограниченный экземпляр без исполнителя задач**: нет сети, прослушивания канала CORE, доступа к owner private key, реального файла-получателя и автоматической очереди.
- Это важная проверка механики службы и файловых прав, **НЕ промышленная интеграция CORE–HOST в её постоянный процесс**. Запуск фактического Qwen → CORE → живой защищённый HOST на пользовательском компьютере ещё не сделан.
- Нет подписи кода издателя, отдельно зарегистрированных owner/reviewer/witness ключей, физического внешнего monotonic highwater, проверенных обновлений и rollback. Комплексный подписанный производственный установщик и реальная независимая приёмка ещё отсутствуют.
- Рабочий ПК владельца, резервный ПК и GitHub self-hosted Windows runner не изменялись, Windows-ресурсы испытывались на изолированном GitHub-hosted машине.
- Артефакт для ревизора хранится ограниченное время, [страница сборки](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39758320407) остаётся источником сведений о нём.

## Что остаётся именно до готовности производственного релиза

1. Уполномоченный владелец и отдельный ревизор подтверждают точный SHA исходников и архив, доверенный сертификат подписания Windows и независимые root-of-trust для трёх участников.
2. Разработать/проверить производственный сервис CORE–HOST без тестовых ограничений с реальным подписанным admission, lease/fence/replay/UNKNOWN, операторским per-service SID и кодом защищённой установки/обновления/отката.
3. Надёжно привязать настоящий установленный Qwen к отдельной защищённой службе (не пропускать подписанное подтверждение владельца, не запускать код Qwen напрямую) и выполнить один непрерывный физический E2E.
4. Организовать независимый witness/highwater вне откатываемого диска и настоящий подписанный verdict для [Issue №11](https://github.com/DSLitvinov1/my_first_repo/issues/11). До одобрения **NO MERGE, NO DEPLOY, NO ACTIVE QUEUE, NO AUTO-EFFECTS, NO SKILLS**.
