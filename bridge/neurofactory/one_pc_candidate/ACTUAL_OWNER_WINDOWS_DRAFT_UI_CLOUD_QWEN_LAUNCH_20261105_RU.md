## Как подключена реальная облачная Qwen без платного API

- На уже существующем Linux `litd12123.clodocd.com` работает Qwen2.5 Coder 1.5B GGUF (SHA256 `cc324af070c2ecbfd324a30884d2f951a7ff756aba85cb811a6ec436933bb046`) через установленный `llama-cli`; модель не скачивалась на Windows и не создаётся платный API. Linux не требует постоянно работающего дополнительного HTTP-порта для генерации: каждый запрос поступает через OpenSSH forced command.
- Создан отдельный ограниченный SSH identity key на Windows в пользовательском `NeurofactoryData\cloud_qwen\id_ed25519` с ограничением NTFS ACL владельцем, ADMIN, SYSTEM; private key **никогда не загружался в GitHub и не передавался Linux**. Host identity проверяется по точному Ed25519 known_hosts, без agent/pty/port-forwarding и без пароля.
- Linux `authorized_keys` содержит **только ограниченный к модели** `restrict,command=\"/usr/bin/python3 /home/cloudagent/neurofactory-lab/cloud-qwen-draft-20261105/forced_ssh_qwen.py\"`; этот ключ нельзя использовать для интерактивной оболочки, произвольных SSH-команд и проброса портов. Серверная программа без shell и файловых эффектов читает один строго ограниченный JSON-запрос, проверяет SHA256 модельных весов, генерирует **только текстовый черновик**, выдаёт SHA256 ответа. Приёмник Windows перепроверяет task ID, случайный nonce, модель SHA, размер ответа и явные `execution_allowed=false`, `owner_signed=false`.
- Linux one-use SQLite попыток `/home/cloudagent/neurofactory-lab/cloud-qwen-draft-20261105/model-attempts.sqlite3` защищён правами пользователя; на момент запуска **3 запроса, из них 1 успешный**. Не использовать этот журнал как независимый witness, он предназначен только для предотвращения случайного повторного запуска модели при ошибке.
- Исправлен фактический вывод `llama-cli`: тот печатает баннер и обратные управляющие символы, а длинный prompt в консоли сокращает как `... (truncated)`. Серверный парсер теперь принимает **только часть после отграниченного вывода prompt**, до метрик. Первая потерянная попытка не повторялась; следующее отдельное задание прошло и вернуло настоящий результат.
- Код server: `cloud_qwen_forced_ssh_server.py` (последняя логика исправлена коммитом `e7c9b247647df4270f64943c96493d7f719afd0a`), клиент: `cloud_ssh_draft_provider.py`, UI: `local_workspace.py`, `draft_provider.py`, `workspace.js`. На Windows весь код входит в пакет `65ee50afbb67eb9795146224b662ae78bc22362a`, серверный код развёрнут отдельно с тем же содержимым, что хранится в исходниках. Системное выполнение, CORE очередь, HASH подписанного HOST, SKILLS и настройки доверенной Windows-службы не изменялись.

## Что остаётся для полного автономного запуска (НЕ выполнено)

1. **Живая производственная Windows-служба CORE/HOST** с правильным постоянным runtime, настоящими полномочиями, protected SID, реальным подписанным witness внутри ОС-службы, reboot/recovery и запретом повторных эффектов. В данный момент работает лишь user-level draft workspace; Windows SCM настоящий процесс как production пока не установлен. Без signer/witness/reviewer нельзя снимать защитные ограничения просто ради галочки.
2. **Независимый аппаратно/административно защищённый от отката серверный журнал** с оператором, которому разработчик не может подменить ключ/эпоху/проверку. На Linux сохранён реальный двухмашинный signed TLS lab с `epoch3`, но лабораторные ключи и SQLite принадлежат тому же управлению, поэтому защищённая производственная независимость отсутствует.
3. **Настоящий CA-issued Authenticode Windows code-signing** после официальной проверки личности правообладателя (KYC/оплата/ключ CA/HSM), и подпись/проверка точного окончательного установщика. Review EXE до сих пор `NotSigned`; нельзя считать самоподписанный сертификат равнозначным.
4. **Человеческая независимая приёмка:** [Issue #11](https://github.com/DSLitvinov1/my_first_repo/issues/11) открыт, нет назначенного независимого уполномоченного ревизора с положительным подписанным решением на точную версию.
