# НЕЙРОЗАВОД — единый центр получения заданий несколькими компьютерами

Дата решения: 15.10.2026. Изолированный координационный контракт. Связан с Issue #14 (TRUSTED HOST), #3 (координатор), #8 (roadmap), CORE #9, REVIEW #11. **Принята целевая техническая архитектура; инфраструктура НЕ установлена и НЕ разрешена к эксплуатации.**

## Архитектурное решение

**Один авторитетный сервер очереди** на собственном доверенном хосте с PostgreSQL и небольшим отдельным доверенным HTTPS-API. Рабочие ПК (Linux/Windows) не читают и не изменяют базу напрямую. Их учётные данные относятся только к коротким запросам API на получение статуса/задачи; приватные ключи внешнего подписанта никогда не передаются работникам. Использование PostgreSQL предложено как целевой единый механизм, но цена и доступный хост ещё не подтверждены; запрещено автоматически создавать платную БД или сервер.

**Отдельный независимый удостоверяющий журнал** (issuer) под собственной OS identity и отдельным хранилищем, закрытыми от CORE, Qwen, рабочих ПК и администратора приложения. Подписывает разрешения и неизменяемые последовательные записи, проверяет внешний доверенный корень ключа и защиту от отката. Размещение на том же физическом устройстве с одним root/admin недостаточно для утверждения изоляции от скомпрометированного root/admin. До независимого deployment/penetration-test: issuer = NOT_IMPLEMENTED.

**CORE** — единственный владелец файлового sandbox/writer и локальных идемпотентных операций, запускаемых только с защищённой отдельной OS identity. **PROVIDERS** — непривилегированный локальный исполнитель с доступом лишь к разрешённому входу, без разрешений переименовывать предков CORE sandbox, читать CORE базу, давать внешнее одобрение или повторять неизвестную операцию. **TRUSTED HOST** — только собственная область: bridge/neurofactory/trusted_host/ и его workflow; будущая ветка neurofactory-trusted-host-owned-20261015 (зарезервирована, ещё не создана; отдельный чат-владелец не принял роль). **COORDINATOR** — только формат контрактов и реестр владельцев.

## Центральная одноразовая транзакция по нескольким ПК

1. **Постановка:** источник с подтверждённой личностью предлагает единственное учебное задание, `task_id`, зафиксированные SHA40 исходного Git-коммита, SHA256 файла и SHA256 снимка задания (не смешивать), approved project/target allowlist, policy version, лимиты нулевых расходов. Обязательна подписанная внешним issuer авторизация. Сервер атомарно `INSERT` с уникальным `task_id` и `input_task_sha256`. Повтор такого же предложения означает только получение существующего статуса; тот же `task_id` с другими байтами/версией отвергать.
2. **Получение разными ПК:** один API `claim` в одной центральной PostgreSQL-транзакции с row lock / conditional state update; один победитель, собственный server-issued `lease_epoch`, `fencing_token` и срок по **времени сервера**. Остальные получают явное `NOT_CLAIMED`, никогда одновременно разрешение. Каждый новый epoch строго больше предыдущего. Потеря связи => STOP; локальные SQLite, GitHub issues и Telegram не заменяют центральный арбитр.
3. **Продление:** heartbeat через тот же центральный API при строгом соответствии task ID, client identity, epoch, token, status и server lease clock. Прежний или чужой epoch отвергается. При истечении lease разрешается переназначение только до стадии `PRE_SIDE_EFFECT`, если защищённый issuer независимо подтверждает отсутствие побочного эффекта. После `PRE_SIDE_EFFECT`, при UNKNOWN или потере квитанции — строго `NEEDS_MANUAL_RECONCILIATION`, без автоматического повторного claim.
4. **Предварительная защёлка:** до необратимой файловой или внешней операции CORE отправляет отдельный атомарный `PRE_SIDE_EFFECT` с неизменяемым idempotency key и epoch. Сервер защищённо сверяет holder и выдаёт одноразовую квитанцию issuer, не разрешая такую же для другого epoch. Без квитанции — STOP, никаких новых побочных эффектов.
5. **Эффект и проверка:** разрешённый writer из защищённого контекста проверяет перед эффектом неизменность предков sandbox относительно OS boundary, действует только в разрешённом каталоге и затем независимо читает содержимое и digest. Для настоящего внешнего побочного эффекта конечный приёмник должен реализовывать idempotency/fencing; **сам PostgreSQL claim не может гарантировать exactly-once запись в произвольную внешнюю систему**. Неизвестный исход — STOP + ручная reconciliation, а не второй вызов.
6. **Завершение:** отдельный подписанный `EFFECT_READBACK` с точным новым source/result digest, идентичностью issuer, `lease_epoch`, `idempotency_key` и монотонным номером checkpoint. Только тогда статус `CHECKPOINTED`; успешная Python CI или метка UI не считаются внешней квитанцией.
7. **Режим отказа:** недоступен central API/PostgreSQL/issuer, подпись устарела, токен чужой, epoch старый, checkpoint rollback или частичный результат — **BLOCKED/UNKNOWN**, хранить неизменённые доказательства, не стирать, не переигрывать и не переключать на другой автономный ПК.

## Точные межкомпонентные контракты

- Внешняя постановка: `schema`, `task_id`, `project_id`, `input_core_sha40`, `source_file_sha256`, `input_task_sha256`, `target`, `policy_sha256`, `max_budget_units`, `authorization_receipt_ref`. По умолчанию execution/publication/retry=false.
- Claim-запрос: `task_id`, `worker_id`, `request_id`, `expected_status=QUEUED`. Claim-ответ: `claim_status` (CLAIMED/NOT_CLAIMED/BLOCKED), `lease_epoch`, `fencing_token`, `server_lease_expires_at`, `issuer_receipt_ref`. Токены являются приватными учётными данными, никогда не помещаются в GitHub Issue, OPS snapshot, UI или Actions.
- Подтверждение: `task_id`, `lease_epoch`, `idempotency_key`, `previous_issuer_sequence`, `intent_digest_sha256`, `receipt_ref`. Система требует монотонную issuer-sequence.
- Отдача модели из PROVIDERS: только связанный task/input SHA ответ `PROPOSED_UNVERIFIED` с digest и подтверждением нулевых платных расходов. Не одобрение REVIEW и не разрешение writer.
- Наблюдение OPS/UI: только безсекретное состояние, точные исходные SHA, время наблюдения и флаг `UNVERIFIED`. `UNKNOWN` показывать как неизвестно, никакие управляющие действия UI не разрешены.

## Обязательные испытания перед первой учебной транзакцией

- Два независимых ПК одновременно claim одной задачи: ровно один победитель и одно issuer approval; повторный `request_id` идемпотентен, конфликтующие входные SHA отвергаются.
- Падение после claim, до pre-effect; истечение lease и stale holder: новый epoch не принимает квитанцию старого. Падение после pre-effect или после внешнего файла, до receipt: `UNKNOWN`, автоматический повтор **невозможен**.
- Защита от повторной/поддельной подписи, отката номерного журнала и от подделки одного лишь локального SHA; секреты недоступны прочим identity.
- Непривилегированный процесс не может переместить/переименовать CORE parent и прочитать SQLite; отдельно тест same-UID, Windows reparse/ACL и условия root/admin, не заявлять полного изолирования без работающей конфигурации.
- Отказ сети/БД/issuer, разрыв соединения, частичная запись, double publisher и unknown delivery; отдельный независимый REVIEW на exact SHA.

## Уточнение после независимой проверки №38724332734 и №38726299649 (15.10.2026)

Независимый REVIEW воспроизвёл реальный дефект **подготовленного** offline-подписанта: даже корректно подписанное `EFFECT_READBACK` без номера аренды или идентификатора эффекта проходило криптографическую проверку. Речь не о работающем production-issuer и не о подделке закрытого ключа. Дефект относится к неполному набору **подписанных** обязательных полей, а не к алгоритму Ed25519.

Контракт версии `v1.1-test-only`: общая часть подписываемого события содержит точный task ID, SHA40 исходного CORE, SHA256 исходного файла и входного задания, событие, номер последовательности, предшествующий digest, контрольную точку, удостоверенные identity/key ID и время. `AUTHORIZE_TASK` не несёт lease/эффект. `LEASE_CLAIM` и `MANUAL_STOP` обязательно добавляют в **ту же каноническую подпись** `lease_epoch` (нативное строго положительное целое число), `worker_id` и `fencing_token_sha256`. `PRE_SIDE_EFFECT` и `EFFECT_READBACK` **обязательно** добавляют все три и `idempotency_key`. При лишнем, отсутствующем, bool/float или неподходящем поле отклонять событие; `signature_base64` отдельно от подписанного `payload`.

Проверяющий MUST получить ожидаемые `lease_epoch`, `worker_id`, `fencing_token_sha256`, `idempotency_key`, `task_id`, source SHA, прошлый digest, issuer public key и следующий номер из **внешнего защищённого контекста**, не из самого подписанного ответа/локальной базы исполнителя. Корректная подпись при истёкшем, чужом epoch/ключе всё равно **DENY**. Если нет независимого значения, STOP / UNKNOWN. Совпадение полей и Ed25519 не удостоверяют физическую сохранность issuer private key, antirollback или принадлежность GitHub reviewer.
