# НЕЙРОЗАВОД — план настоящей приёмки на ДВУХ РАЗНЫХ ФИЗИЧЕСКИХ компьютерах
Дата 17.10.2026. Статус: PLAN ONLY, NOT EXECUTED. Владелец COORDINATOR #3, собственная рабочая ветка без объединения. Не перепутать два Linux UID одного GitHub Actions runner с двумя физическими устройствами.

## До испытания
1. Владелец письменно утверждает два уникальных авторизованных устройства (machine A/B), разрешённый одноразовый репозиторий/fixture проект, отдельную машину или компонент доверенного HOST, оператора независимого подписанта, владельца постоянного trust pin и ревизора. Все настоящие ключи должны генерироваться только на их защищённом месте, не в Issue/GitHub/AI-чате/Actions. Не переносить токены/пароли в переписку.
2. Подтвердить физическую независимость устройств: разные идентификаторы хоста и системные серийные номера показываются ответственному проверяющему только внутри локального защищённого журнала (не публиковать аппаратные серийные номера); разные сеансы ОС и защищённые учётные записи. GitHub-hosted runner + второй процесс на том же физическом runner не подходят.
3. Разграничить права: owner policy и private signer key — только у операторского UID; DB actor не пишет/не читает их; CORE/модель не владеют конечным файлом и не открывают raw writer; только OS-receiver владеет целевой тестовой директорией. Уничтожить пробы/фикстуры по завершении.
4. Согласовать root доверия, аутентифицированный транспорт и независимый durable highwater, резервную копию и независимый протокол восстановления. Нет production до доказательств на устойчивом состоянии.

## Адресные сценарии
A. Две авторизованные машины запрашивают **одну** bounded учебную задачу на одном исходном Git SHA. TRUSTED HOST выдаёт ровно одну активную аренду и operator-signed, owner/repo/project/source/worker/file/fence/idempotency bounded permit.
B. Конечный получатель на отдельной системной роли непосредственно в точке O_EXCL/final effect проверяет signed issuer key из independently pinned root, owner policy, текущую аренду и неизменную исходную версию, атомарный журнал операций и защищённый высокий водяной знак. Только один временный тестовый файл: exact bytes SHA before/after.
C. Второй воркер с устаревшим epoch, потерянным соединением, неправильным task/repository/source/owner/target и повторной доставкой — каждый получает DENY и ноль дополнительных файлов.
D. Сбой ПО после fsync до подтверждения, затем reboot реального физического хоста и restore из предыдущей копии БД: состояние UNKNOWN, автоматический повтор необратимого эффекта запрещён; ручная сверка с диском/защищённым операторским head, подтверждение отсутствия повторного эффекта.
E. Подмена владельца/ключа, возвращение старого подписанного root, запрет чтения ключей через DB и клиента, изменение policy (независимое утверждение оператора), отключение доверенного подписанта, запрет старого прямого CORE writer.
F. При только что подтверждённом независимом владельцем разрешении запустить ограниченную Qwen на доступном CPU/GPU без платного API, получить *новую* незаглушечную проверяемую generated suggestion, допустить его к применению только через отдельные CORE/HOST OS-receiver проверки. Если ресурсы недоступны — остановиться без записи.

## Проверяемые доказательства
Для каждой попытки: точные SHA исходных версий CORE/HOST/COORD/PROVIDERS и ключевых policy records, monotonic sequence, UTC-время и корреляционный ID операции, отдельные локальные ID двух реально разных компьютеров без разглашения private machine identifiers, снимки lease/fencing до/после, независимые журналы единственного эффекта, bytes SHA, отдельно сохранённый hash head после восстановления, исходящие ограничения и signed verdict независимого уполномоченного ревизора. Review №11 только при внешнем полномочии принимает окончательный выпуск. Не выдавать своё CI либо чат второго ИИ за независимую приёмку.

## Жёсткий стоп
Любой потерянный root/owner permission, mismatch, duplicate, ambiguous result, signer unavailable, resource gap, неразрешённый storage path или отсутствие человеческого независимого release verdict ⇒ **REJECT LIVE**.
