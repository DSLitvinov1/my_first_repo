# НЕЙРОЗАВОД — минимальный контракт безопасного учебного MVP (только координация)
Сверка: 15 октября 2026 года. Связанные задачи: [общее #8](https://github.com/DSLitvinov1/my_first_repo/issues/8), [CORE #9](https://github.com/DSLitvinov1/my_first_repo/issues/9), [REVIEW #11](https://github.com/DSLitvinov1/my_first_repo/issues/11), [UI #10](https://github.com/DSLitvinov1/my_first_repo/issues/10), [OPS #6](https://github.com/DSLitvinov1/my_first_repo/issues/6). Этот документ **не код**, не выдаёт разрешение на исполнение и не меняет чужие ветки.

## Единственная проверяемая цель

Одна явно одобренная **учебная** задача с allowlist ровно одного безопасного sandbox-проекта. Проектный владелец определяет ожидаемый выход, верхнюю границу ресурсов, обязательную локальную тест-проверку и безопасные пути. Входная задача не даёт произвольных полномочий на файловую систему, платный API или публикацию. Все действия выполняются в изолированной ветке/среде только после отдельных ворот; HANDOFF по-прежнему PAUSED_BY_USER.

## Одно направление — одна зона и один источник результата

1. **COORDINATOR (этот чат)**: только текстовый контракт полей и состояний, реестр owner и расходных запретов, контроль допусков/ссылок на evidence, оценка конфликтов. Запрещено выполнять CORE lease, провайдерскую модель, UI-код, подписывать независимый REVIEW или автоматически писать общие задачи. Координаторский журнал, а не чужая очередь, хранит ссылку на последнюю проверенную версию.
2. **CORE (чат «Нейрозавод 1», Issue #9)**: единственный владелец задач, claim, lease, атомарного изменения статуса, попыток, remote checkpoint и идемпотентной квитанции. Получает только разрешённый project ID, task ID, exact input commit/digest, approved sandbox, идентификатор provider-заявки, максимальную попытку. При двух concurrent claim один должен получить явный отказ. UNKNOWN side effect/receipt — STOP, запрет повторной публикации, только независимый readback.
3. **PROVIDERS (Issue #5, PR #7)**: только локальное Qwen inference (дизейбл по умолчанию, loopback-only) и own durable attempt budget, не выдаёт решение REVIEW, не мутирует очередь и не работает с внешней сетью/платным API. Возвращает однозначный provider/model identity, task ID, ответ/ошибку, оценку бюджета, verified/offline_mock признак; при неизвестном исходе STOP, не повторять. Локальная модель не подтверждена установленной на Windows; не заявлять работающий реальный E2E.
4. **REVIEW (Issue #11)**: независимые проверки exact CORE SHA только после появления нового CORE-коммита. Требует данные из неизменяемого внешнего GitHub run/artifact и независимого авторизованного reviewer, а не строковое APPROVE модели. Ни один автор проверяемого кода не может сам утвердить свой результат. REVIEW не правит CORE.
5. **SKILLS (PR #542, отдельная Issue #543)**: 12 registry candidates, ноль активных; внешнее удостоверение reviewer пока не реализовано. Может готовить metadata предложения для проекта, но не запускать изменение файлов или подключать навыки в CORE до внешнего approve. Не переносить целиком старые конфликтующие PR.
6. **OPS (Issue #6)**: только read-only отчёт по предоставленным недоверенным снимкам, при отсутствии данных — UNKNOWN. Не разрешать recovery, retry, merge или release. Proven stable candidate b908b78f35dcdd7a88eb0d939c748df0c5856328 прошёл собственные 20 GitHub jobs; эксперимент 08645ded5ee5588e709efb00ee9c965cd7a6fdcf с защищённым чтением — отдельная версия без независимого заключения и без доказанного Windows regression.
7. **UI (Issue #10, отдельный владелец ещё не назначен)**: только новая директория bridge/neurofactory/control_ui/ и исключительно собственный workflow. Пока read-only демонстрационная панель над **явно симулированными** статусами, без GitHub credentials, live runners, записи задач или вызова CORE/PROVIDERS. Статус UNKNOWN честно показывается неизвестным. Конкретную ветку создаёт будущий одобренный UI-владелец; координатор не создаёт ему ветку и не меняет его код.
8. **HANDOFF**: пользовательская пауза; не оживлять модельную цепочку, Q090, publisher или отправку в ChatGPT под видом теста MVP.

## Минимальная информационная граница

Сущности данных — только спецификация, без автоматических действий:
- Проект: фиксированный идентификатор, утверждённый sandbox-каталог/ветка, allowlist, ограничения расходов = ноль платных сервисов, ожидаемая детерминированная проверка.
- Задача: уникальный устойчивый ID, snapshot exact input SHA, owner CORE, статус QUEUED/CLAIMED/RUNNING/UNKNOWN/BLOCKED/CHECKED, attempt и lease version; запрет пересечения чужих файлов.
- Результат PROVIDERS: ID задачи, локальная модель/версия или mock, однозначная ошибка; никоим образом не REVIEW verdict и не external delivery permission.
- Доказательство: exact source/tree SHA, идентификатор GitHub run/job/artifact, контрольная сумма, независимый канал получения и криптографическая/платформенная привязка reviewer identity. Нет происхождения — статус UNKNOWN, не APPROVED.
- Отображение: UI и OPS получают только минимально необходимые read-only поля и явно фиксируют источник/время наблюдения и ограничения доверия. Никакой секрет, токен, приватный промпт или пароль в сводку не передаётся.

## Последовательные ворота — без старых дублей

**Gate A (выполнить CORE-владельцу):** появился новый exact CORE commit с проверкой одновременных claims, crash до/после side effect, corrupted checkpoint, UNKNOWN receipt STOP и отсутствия чужих writes. До этого все реальные исполнительные E2E заблокированы.

**Gate B (выполнить REVIEW независимо):** собственный аудит только нового Gate A SHA и origin-bound GitHub evidence. Green CI или анонимная модель не являются независимой подписью. Если FAIL — изолированная ошибка P1 с воспроизводителем.

**Gate C (выполнить PROVIDERS-владельцу):** source + offline tests Windows/Linux на одном exact SHA (PR #7 current f25b67fe9e66998c7291e2dbc26e139abe8b04cc), отдельная независимая проверка journal/lock, подтверждение установленной локальной модели без скачиваний и без платного вызова. Не повышать статус автоматически.

**Gate D (выполнить координатору после A/B/C):** выбрать один одобренный sandbox-проект и одну безвредную задачу с явным лимитом; сформировать письменное разрешение на единственный изолированный E2E, не в production и не в пользовательские репозитории без доступа. Новое разрешение может потребоваться, если HandOFF/модельный процесс по факту задействуются. Пока A/B/C отсутствуют, Gate D BLOCKED.

**Gate E:** только после собственных E2E evidence и независимого решения рассмотреть GitHub merge и более широкие проверки. Рабочая публикация/ChatGPT отправка/HANDOFF и платные API не разрешены. Все оставшиеся ворота branch protection, trusted reviewer и once-only external publisher не упраздняются.

## Конфликт приоритетов и эскалация

В Issue #8 буквы «P0/P1» обозначают **очерёдность задач**, а в координационной P0/P1/P2 политике — **серьёзность инцидента**. Не трактовать высокий приоритет MVP как инцидент P0 и не отменять защитные ворота ради скорости.

P0 STOP: действительная опасность утечки/неавторизованной записи, платного запроса, HANDOFF, повторной публикации. P1 BLOCK: доказанный баг/ложный REVIEW/отклонённый новый CORE или providers contract. P2 WAITING: нет нового CORE SHA, нет независимого аудитора OPS, нет Windows/Skills signoff, нет UI-owner. Два неизменных прохода без событий — не создавать статусы/коммиты ради видимости работы.

## Следующее событие для координатора

Открывать повторно только при новом CORE exact SHA, фактическом Windows-run+independent review PROVIDERS, независимом подписанном Skills/OPS verdict, принятии UI роли или прямой новой инструкции пользователя. Issue/PR документирует поручение, но не обеспечивает фактическое выполнение другими ChatGPT-чатами. Никаких background promises.
