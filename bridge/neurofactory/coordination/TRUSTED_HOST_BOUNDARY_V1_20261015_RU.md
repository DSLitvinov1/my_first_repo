# НЕЙРОЗАВОД — межкомпонентный контракт доверенной границы CORE / PROVIDERS

Дата согласования координатора: 15 октября 2026 года. Статус: **проект интерфейса для владельцев**, строго без разрешения исполнения, merge, платных API или публикации. Связанные задачи: CORE #9, независимый REVIEW #11, координация #3, дорожная карта #8, PROVIDERS PR #13.

## Почему это следующий необходимый интерфейс

Независимый REVIEW протестировал точный CORE SHA `ef8ce6acc64ac1d4ad2c8e8018e67e28b8549fe3`, собственный REVIEW SHA `5f4259793e2b21503ef3b7865b2cb9e05e17fd3a`, Actions `38661559153`, Issue #11 comment `6181724062`. Вердикт **REJECT для рабочего запуска**. Предварительно защищённый отпечаток обнаруживает согласованную подделку SQLite+файла. Однако CORE только сравнивает переданный SHA-256; не создает доверенного внешнего регистратора/подписи. Файловый writer на POSIX всё ещё пишет в перемещённый вне песочницы каталог при атаке владельца с тем же UID, прежде чем возвращать STOP. Windows writer намеренно отключен. Это разные открытые риски: внешний регистратор **не исправляет** файловую изоляцию, а изоляция **не создаёт** подписанного квитанционного журнала.

## Предлагаемая граница владения (не реализована)

1. **CORE owner:** единственный издатель состояния задачи/lease и файловых транзакций под *отдельной защищённой OS identity*, которой не владеет Qwen, обычный пользовательский runner или низкопривилегированный PROVIDERS. Только CORE оформляет события намерения до побочного эффекта и переходы после доверенного readback. Если нельзя доказать недоступность parent-каталога для rename/move другим процессом с фактическими правами writer, единственный разрешённый исход — **STOP до эффекта**.
2. **Отдельный trusted anchor issuer:** внешний по отношению к CORE и его SQLite каталогам защищённый сервис/хранилище под иной identity, с неизвлекаемым из CORE ключом подписи (или эквивалентной платформенно удостоверенной записью), монотонным неоткатываемым счётчиком и строгим сравнением предыдущего значения. CORE и PROVIDERS имеют только право предложить новое событие, **не** переписать старую запись, поменять owner/signer или задним числом подтвердить самих себя.
3. **COORDINATOR:** зафиксировать JSON-схему согласования и обязательные отрицательные проверки; не хранить подписи, секреты/ключи, защищённые квитанции и не осуществлять issuer/CORE операции. Любая read-only проверка по текущим собственным модулям сохраняет `external_origin_attested=false`, `publication_allowed=false`.
4. **REVIEW:** отдельная роль, независимо сверяющая код, контрольные суммы, actor identity/аудируемый exact SHA и отрицательные случаи. Собственный GitHub Actions `SUCCESS` и комментарий GitHub — свидетельства тестирования, но не автоматически защищённая подпись issuer.
5. **PROVIDERS:** получает только модельные входные данные с закреплённым source SHA, отдельным SHA256 задания и ограниченными ресурсами; хранит у себя приватный сырой ответ, отдаёт минимальные контрольные суммы, не подписывает одобрение, не пишет файлы CORE и не делает повтор при неизвестном исходе.

## Обязательная форма записи журнала issuer (предлагаемая схема)

Каждое неизменяемое событие должно иметь точные поля (прочие поля — отказ):

- `schema`: `neurofactory.trusted_checkpoint_event.v1`; `task_id`; `project_id`; `input_core_sha40`; `source_file_sha256`; `input_task_sha256` — **три разные сущности**, никогда не подменять одну другой.
- `event_kind`: строго из `AUTHORIZE_TASK`, `LEASE_CLAIM`, `PRE_SIDE_EFFECT`, `EFFECT_READBACK`, `MANUAL_STOP`; без неявного `REVIEW_OK` или `PUBLISHED`.
- `event_sequence`: целое положительное число, строго увеличивающееся для task ID; `prior_event_digest_sha256`: заранее закреплённый предыдущий отпечаток для данной задачи, у начальной записи — строго согласованный genesis-marker.
- `core_checkpoint_digest_sha256`: точное значение из CORE `checkpoint_fingerprint()`, вычисленное после независимого верифицированного чтения, а не произвольное последнее вычисление из файлов нарушителя.
- `issuer_identity`: удостоверенная identity внешнего регистратора; `issuer_key_id`; `issued_at_utc` — используемые только вместе с проверкой допустимости identity, ключа и доверенного времени.
- `signature`/platform immutable receipt: подпись над всеми предыдущими каноническими полями, проверяемая **вне** SQLite/CORE/PROVIDERS, включая точный номер последовательности, source и тип события.

Схема — предложение для будущего владельца доверенного регистратора. На данный момент нет закреплённого issuer, проверенных ключей, протокола канонизации, анти-rollback реализации и подтверждённого независимого платформенного receipt. Никому нельзя самостоятельно объявлять её «готовой».

## Атомарность, остановка и устойчивость

- До файлового эффекта CORE фиксирует durable `PRE_SIDE_EFFECT` и получает защищённое подтверждение issuer. Если подтверждение не произошло или исход неизвестен, **STOP без нового эффекта**.
- После эффекта CORE выполняет доверенное чтение файла, сверяет точную прежнюю Git-версию/новый SHA и получает отдельную неизменяемую `EFFECT_READBACK` квитанцию. До этого статус `UNKNOWN / NEEDS_MANUAL_REVIEW`, а не `COMPLETED`.
- `event_sequence` и предыдущий digest защищают от перестановок и подмены старых событий; при разрыве цепочки, старом или повторном номере, неправильном signer/source — fail closed. Квитанция «таймаут/неясно» не повод ещё раз отправлять модель или записывать файл.
- Взаимное исключение существующей SQLite относится только к процессам на **одной** машине с одной БД; оно не обеспечивает distributed CAS. Для нескольких мостов потребуется отдельный совместный авторитетный lease/epoch и подтверждение fencing на стороне issuer/CORE.
- Отдельная OS identity и права каталогов должны быть независимо проверены атакующими тестами на rename/move и symlink/reparse. **Наличие O_NOFOLLOW/dirfd не равно изоляции от процесса, имеющего право перемещать тот же inode**. На Windows файловый writer остаётся выключенным до независимой защищённой реализации.
- Значения модели, статус SKILLS, UI карточка и snapshot OPS — *не* полномочия на запись или публикацию, независимо от «зелёного» отображения.

## Требования к приемке владельцев

**CORE #9 / инфраструктурный owner:** документировать реальную выбранную OS identity, ACL/directories, issuer placement, key custody, журнал и правила устойчивого подтверждения; подготовить точный собственный commit, только изменённую безопасность проверить негативными случаями. Не перекладывать секретный ключ issuer в GitHub Issues, Actions логи или координационные файлы.

**PROVIDERS PR #13:** согласовать envelope неизменной задачи, сырые ответы оставить в собственном защищённом каталоге; не считать приватный локальный receipt внешней подписью; никакой real Qwen до подтверждения ресурсов, Ollama и всех разрешений.

**REVIEW #11:** при новом CORE и issuer exact SHA независимо проверить same-UID перемещение каталога **без побочной записи**, согласованную SQLite+файловую подделку с атакующим, пытающимся подставить новый «внешний» SHA, повтор/откат sequence, аварийные UNKNOWN, source scope и подписанное происхождение. Результат привязать к точному коммиту.

**OPS #6 / UI #10 / SKILLS #543:** строго read-only и неактивно, пока нет независимого допуска; три слоя UI не должны извлекать полномочия из view.

## Решение координатора

`REVIEW_REJECT_LIVE` для CORE `ef8ce6acc64ac1d4ad2c8e8018e67e28b8549fe3`. `TRUST_ISSUER=NOT_IMPLEMENTED`. `SAME_UID_CONTAINMENT=NOT_PROVEN`. `WINDOWS_FILE_WRITER=DISABLED`. `CROSS_HOST_CAS=NOT_IMPLEMENTED`. `MODEL=NOT_RUN`. `HANDOFF=PAUSED_BY_USER`. `RELEASE=BLOCKED`.

Это пригодный к обсуждению/реализации межкомпонентный контракт, **не доказательство реализации**. Снимать блокировку только после отдельно проверенных доказательств новых границ.
