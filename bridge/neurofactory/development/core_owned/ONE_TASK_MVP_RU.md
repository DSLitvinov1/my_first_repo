# CORE / однозадачный исполнитель — границы первой кандидатной версии (15.10.2026)

**Владелец:** CORE, Issue #9, ветка `neurofactory-core-queue-owned-20261013`. Статус **CANDIDATE / WAIT_INDEPENDENT_REVIEW**. Ни объединения, ни реальной Qwen-генерации, ни публикации результатов из этой реализации.

## Что реализовано

- `one_task_core.py`: в *приватном* доверенном локальном каталоге поддерживает максимум одну запись задания. Приём задачи возможен только при положительной внешней проверке реального разрешения доверенным хостом и проверке закреплённого Git-коммита, HEAD, исходного содержимого из Git-дерева и SHA-256. Никакого разрешения от текста модели или поля `approved`.
- До приёма фиксируются: точные `task_id`, `project_id`, исходный commit SHA, разрешённый **один** путь внутри `bridge/neurofactory/development/core_owned/`, источник SHA-256, цель и ограничение ресурсов. Для нового (не существовавшего в Git на исходном SHA) файла `source_sha256` — SHA-256 от пустых байтов. Для существующего файла песочница **до** выполнения должна содержать побайтово равную Git-версию.
- `BEGIN IMMEDIATE` + SQLite `synchronous=FULL`: одновременно получает задачу максимум один процесс из нескольких процессов, обращающихся к **одной** приватной SQLite базе на **одной** машине. Секретный токен в БД хранится только как SHA-256. Первое получение окончательно потребляет попытку; нет автоматической повторной выдачи после истечения lease.
- `apply_offline_test`: принимает только один точный синтетический текстовый ответ с явным `OFFLINE_TEST`. Перед файловым эффектом записывает и подтверждает устойчивое состояние `APPLYING`; затем пишет только допустимый файл через временный файл/атомарную замену и проверяет чтение обратно, сохраняет итоговый digest и нефальсифицируемые *для самой программы*, но **не подписанные независимым субъектом**, признаки `model_invoked=false`, `review_approved=false`, `published=false`.
- `recover`: истёкшее неопределённое состояние `CLAIMED`/`APPLYING` переходит в `NEEDS_MANUAL_REVIEW`, без повторного вызова или публикации. Порча файла после контрольной точки переводит его в то же состояние. Повторная попытка занять слот запрещена даже после успешной тестовой фиксации.
- `provider_preview`: возвращает предварительный пакет `neurofactory.coordination.provider_bridge.v1` с точным шестипольным вложенным `neurofactory.providers.request.v1` и полным доверенным сопоставлением `binding`. Путь CORE под `core_owned/` детерминированно отображается в `src/` (обычные файлы) или `docs/` (Markdown); исходный CORE-путь никогда не заменяется предложенным исполнителем. `input_sha256 = SHA256(canonical JSON полного одобренного CORE-манифеста)`, **отдельно** от `permissions`, где execution/retry/publication/paid_api все равны `false`. Это подготовка данных, не живое подключение. COORDINATOR #3 должен согласовать digest, mapping путей и источник разрешения. До согласования нельзя включать реальный PROVIDERS.

## Границы безопасности, не скрывать

1. Внешний `trusted_approval_check` — обязательный доверенный адаптер подлинности разрешения; заглушка в тестах на синтетическом Git **не является** настоящим одобрением. До реализации/подтверждения авторизованного источника разрешений реальный ввод в очередь заблокирован операционно.
2. SQLite обеспечивает взаимное исключение только при общем локальном хранилище. Два независимых Windows-моста с разными дисками / доверие к сетевой SMB-блокировке **не проверены**: не включать несколько хостов и не переносить live-очередь. Общий GitHub CAS / центральный арбитр остаётся задачей интеграции.
3. SQLite и локальные квитанции не подписаны отдельно. Тот, кто способен изменять приватную БД, теоретически может подделать её с согласованными полями. Требуется внешняя доверенная резервная копия/remote checkpoint с версионированием/монотонностью, прежде чем запускать недоверенных исполнителей. GitHub Actions сохраняет только **отдельную синтетическую квитанцию испытания**, а не рабочую БД.
4. `0700` POSIX защищает приватные каталоги от других пользователей; защита от враждебного процесса **с тем же UID** и гонок перенаправления пути не доказана. Windows ACL и reparse-point/handle-поведение требуют отдельной проверки доверенного хоста. Нельзя считать Python-функцию безопасности полноценной OS-песочницей.
5. Никакие произвольные Python-колбэки модели не исполняются внутри CORE. Модель может вернуть только инертный текст; её процесс должен быть изолирован внешним исполнительным хостом, без доступа к БД и Git-креденциалам.
6. Никаких платных API, загрузок моделей, GitHub-публикации, независимых verdict, реального Qwen, Windows-рестартов, сквозной межхостовой транзакции. HANDOFF paused, SKILLS off.
7. Контрольная точка `CHECKPOINTED_TEST` **не** означает `SOURCE_VERIFIED` в COORDINATOR и не удовлетворяет независимому REVIEW. До независимого APPROVE запрещено объединение и live-переход.

## Быстрая проверка

`test_one_task_core.py`: изолированный локальный Git fixture, конкуренция трёх отдельных процессов, отрицательные случаи token/approval/path/commit/content, повтор и аварийное восстановление, сохранение и чтение checkpoint. Адресный workflow `neurofactory-core-owned-once-test.yml` запускает **только** новые тесты, без реального Ollama/Qwen, и сохраняет санитизированную квитанцию в GitHub Actions artifact с `retention-days: 14`.
