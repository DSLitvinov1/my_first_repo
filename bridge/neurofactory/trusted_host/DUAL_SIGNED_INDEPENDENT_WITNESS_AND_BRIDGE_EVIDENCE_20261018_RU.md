## Практическая защита от нового риска

Предыдущий TLS witness резервировал операции по правильному сертификату получателя и структурной проверке данных, но **не проверял независимым способом**, что запрос на конкретную операцию подписан как центральным HOST-выдавателем, так и владельцем проекта. При компрометации разрешённого получателя можно было резервировать произвольные допустимые по формату задачи и файлы (вызвать отказ в обслуживании), не имея подписи владельца.

Новый `bridge/neurofactory/trusted_host/offline_witness_signed_scope_gate.py`, blob `7cb0e1e1a12081070149836a783c585f9c013a1d`: операторский pin issuer и owner Ed25519 public keys хранится в закрытой папке **системного пользователя журнала** `nf_witness` вне PostgreSQL и вне прав CORE/model/receiver. Журнал повторно проверяет криптографические подписи над точными owner/repository/project/task/source_sha40/worker/target/content_sha256/operation/lease_epoch/TTL/permit_digest, логическую owner ID и отдельный numeric GitHub user ID `151650108` с repo ID `723328237`. Входящие клиентские публичные ключи не используются для принятия решения. Отсутствие закрытой политики, фальшивая подпись, чужой проект, файл, другая контрольная сумма или аренда — запрет до резервирования.

`offline_mtls_witness_transport.py`, blob `685ae5f9f3402462d612fbd717657e210a1e13df`: новый строго учебный `test-serve-scoped-once` принимает подписанную структурированную операцию через ранее проверенный TLS 1.3. В отличие от старого учебного варианта он вызывает независимый verifier до `reserve()` и защищённого fsync; прежний тест-only маршрут оставлен для регрессии, не объявлен production.

`offline_operator_gated_receiver.py`, blob `f040a69e63a405d9a75a87d621c0f9e3f2c5ee9c`, и `offline_os_separated_effect_receiver.py`, blob `8368ab395229389e50c773363feeaaab20f34a63`: защищённый учебный файловый получатель V4 передаёт подписанные issuer permit и owner grant дальше по TLS для **повторной независимой криптографической проверки на удалённом по OS UID журнале**, до внебазового резервирования, собственного UNKNOWN, проверки реальной PostgreSQL аренды и fsync одного разрешённого тестового файла. Прежние V1–V3 существуют только как OFFLINE_TEST fixtures; не деплоить напрямую.

## Запреты и блокировки

1. Второго физического авторизованного независимого Linux witness-компьютера нет. Все проверки на GitHub-hosted Linux, не на пользовательском Windows. На одном runner root может изменить все отдельные UID; rollback снимка ВСЕГО runner — вне доказанного контроля.
2. Криптографические owner/operator/test issuer keys были созданы временно; реальный владелец GitHub ещё не закрепил постоянный личный Ed25519 публичный ключ через уполномоченного отдельного оператора. Подтверждённый ранее GitHub admin login ≠ криптографическое enrolment.
3. Реальный межмашинный protected listener ещё не одобрен и не развернут: прототип ограничен `127.0.0.1`, одно соединение, отдельные временные сертификаты. Нет физического power-cycle, реального restore PostgreSQL на авторизованной машине с сохранным journal на другой.
4. Независимый назначенный REVIEW #11 должен отдельно проверить точные версии (включая V4) и подписать verdict. Собственные тесты, комментарии в GitHub, совпадение UUID и один общий исполнитель не заменяют независимую приёмку.
5. Производственная очередь OFF, HANDOFF PAUSED, платные API не используются, PR не объединяются, пользовательские компьютеры не изменены.

## Следующее действие

После восстановления доступного резервного соединения или отдельного подключения второй разрешённой физической машины независимо удостоверить настоящий owner/repo key и machine identity, развернуть защищённый witness с отдельным защищённым root, проверить настоящий reboot HOST и rollback локальной базы при внешне живом journal, исключить auto replay, оформить независимый подписанный verdict. До этого **REJECT LIVE**, можно выполнять только изолированную разработку.
