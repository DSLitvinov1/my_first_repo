# НЕЙРОЗАВОД — режим одного Windows-компьютера
Дата: 18.10.2026. Решение пользователя: **не требовать второй физический ПК или Linux-сервер** для локальной версии. Это решение **не отменяет** проверки прав, отрицательные сценарии и независимый REVIEW.

## 1. Целевой режим
`ONE_WINDOWS_PC_LOCAL_PILOT`: все исполняемые компоненты располагаются на одном авторизованном Windows-компьютере. Связь через локальные защищённые интерфейсы; управление может быть открыто в браузере этого компьютера.

| Компонент | Размещение на одном ПК | Граница полномочий |
|---|---|---|
| Панель управления / COORDINATOR | локальный процесс или localhost | чтение статуса, формирование предложений без прямого выполнения |
| CORE + очередь | отдельный обычный пользователь Windows | работа только с одобренными задачами и собственными каталогами |
| Windows TRUSTED HOST | SCM-служба с **restricted per-service SID** | запись только в выделенный каталог и только по проверенной операции |
| Локальная модель Qwen | отдельный непривилегированный процесс при наличии RAM/CPU | не имеет приватного ключа владельца, прав к HOST и обходного права записи |
| База SQLite для локального пилота или PostgreSQL при проверенной установке | тот же компьютер, каталог под ограниченными правами | транзакции, контроль аренды, журнал и резервное копирование |
| REVIEW | независимая проверка точных SHA и доказательств, возможна удалённо через GitHub | reviewer не может авторизовать действия вместо владельца |

**Никакая из перечисленных частей не объявляется установленной на ПК пользователя этим документом.** Подключение моделей и UI на данном exact SHA не подтверждено сквозным испытанием, помечать UNKNOWN.

## 2. Безопасный локальный режим
- Сохранить `HANDOFF=PAUSED`, `production_queue=OFF`, `live_execution_allowed=false` до отдельного согласованного режима допуска.
- Для безвредных учебных действий использовать подписанный owner grant, точный SHA Git/задачи, одну эксклюзивную операцию, защищённый журнал намерения **до** эффекта, fsync и UNKNOWN_NO_AUTO_RETRY при неопределённости.
- У CORE и модели нет доступа к приватному ключу владельца, папке и служебному токену HOST. Windows-служба никогда не получает привилегий администратора и не публикует результаты вовне самостоятельно.
- Создавать отдельно ограниченного пользователя для CORE и уникальный restricted Service SID для службы, а не полагаться только на общий LocalService SID. Проверять действующий токен процесса и DACL, а не название учётной записи в конфигурации.
- Все опасные/внешние побочные эффекты (запись в пользовательские проекты, публикация, удаление, оплаты, реальные сообщения) остаются под отдельным разрешением и независимой проверкой. Не включать автоматическую повторную доставку UNKNOWN.
- Для простого локального пилота SQLite возможна; **не** считать локальную SQLite свидетелем, независимым от отката диска. PostgreSQL на этом же ПК также не является независимым свидетелем.

## 3. Одна машина ≠ независимая защита от полного отката
На одном физическом диске привилегированный администратор/вредоносный код могут одновременно подменить исполняемый код, базу, журнал, ключи и состояние HOST. Даже hash-chain, локальный PostgreSQL и Windows restricted SID не дадут сильной гарантии против полного отката этого компьютера.

Разумные компенсации:
- ежедневные резервные копии за пределами основного каталога, с проверкой восстановления;
- вынос коротких контрольных хешей/подписанных квитанций в независимое удалённое хранилище **опционален**, не требует второго ПК владельца, но требует сети и отдельно управляемых полномочий;
- отдельная регистрация и управление реальным ключом владельца через доступный Windows CNG/TPM/операторский ключ, после согласования криптоалгоритма с тестовым Ed25519; производственные ключи никогда не генерировать в GitHub Actions или сохранять в репозитории;
- при отсутствии независимого удалённого свидетеля **не заявлять** «неоткатываемый», «exactly once» при полном откате ОС или «high-assurance production».

## 4. Однокомпьютерная приёмка
Новая норма **для LOCAL_PILOT**: **один** разрешённый физический Windows ПК. Не проводить и не требовать испытаний на другом ПК владельца.

На этом **одном** ПК отдельным согласием оператора проверить:
1. Настоящий токен службы, уникальный restricted Service SID, доступ модели/CORE к папке HOST = DENY.
2. Пять отрицательных сценариев: поддельная подпись; просроченное разрешение/lease; повторная доставка; чужой project/target; сбой после UNKNOWN, без автоматического повтора.
3. Один успешный безвредный файл от подлинной CORE SQLite/Git-задачи с полной квитанцией.
4. Остановку/запуск службы, а при отдельном согласии — реальную перезагрузку **этого же** ПК с до/после контрольными точками и проверкой сохранности состояния.
5. Проверку восстановления из резервной копии без повторного необратимого выполнения, различая process crash, OS reboot и полный откат образа.
6. Отдельный независимый **REVIEW** точных SHA и собранных фактов. Ревизор не обязан пользоваться вторым компьютером пользователя; достаточно проверяемой независимости личности и полномочий.

Пока только одноразовый Windows GitHub runner подтверждает работу *тестовой* изолированной службы. Реальный пользовательский ПК ещё не испытан. GitHub runner не подтверждает физическую идентичность пользовательского устройства, полную перезагрузку или реальную независимую безопасность.

## 5. Практический CI-эксперимент на одном ПК
Изолированный тестовый workflow `neurofactory-one-windows-pc-full-cycle.yml` использует **ОДНУ** GitHub-hosted Windows-2025 машину и **последовательно**, а не на двух разных машинах, запускает:
- normal: поддельная подпись отклонена, одна безвредная задача CORE, повтор и crash-restart безопасно отклонены;
- crash-window: отдельная имитация смерти реальной SCM-службы после fsync UNKNOWN до создания файла, последующий запрос отклонён;
- между сценариями требует полного удаления временной SCM-службы и тестовых каталогов и неизменности локальной машины.

Тест синтетический и предназначен только для защиты регрессий. Он сам по себе не устанавливает ничего на пользовательский ПК.

## 6. Что нужно для законченного локального продукта
- Исправить оставшиеся контрактные расхождения между CORE/HOST, доработать систему управления моделями и панель UI в их **собственных** ветках. Не смешивать HOST-код и чужие зоны ответственности.
- Подготовить ограниченный пакет установки с явным выбором режима `ONE_WINDOWS_PC_LOCAL_PILOT`, параметрами выделенного Windows-пользователя, службы, каталога и резервирования. До owner approval — только read-only preflight и план установки.
- Провести реальные одноузловые локальные испытания по пункту 4 с оператором. При текущем доступе к пользовательскому компьютеру установка и реальные тесты не подтверждены.
- Получить независимое заключение REVIEW с пониманием **пониженной модели угроз для одного ПК**, а не копировать статус «две физические машины проверены».
- Отдельно получить согласие владельца на использование с реальными файлами. Без этого любой релиз остаётся в режиме CANDIDATE/RELEASE BLOCKED.

## 7. Конкретные запреты
**Никакой второй физический компьютер пользователя не нужен для локального пилота.** Не объединять PR, не устанавливать службы на ПК, не запускать реальные очереди/модели/публикации, не использовать платные API и не утверждать самостоятельного независимого REVIEW до его фактического проведения.
