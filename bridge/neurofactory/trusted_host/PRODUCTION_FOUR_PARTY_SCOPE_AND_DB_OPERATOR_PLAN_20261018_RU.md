# НЕЙРОЗАВОД — производственный контур доверия: подготовка без активации
Дата: 18 октября 2026. Владелец компонента: TRUSTED HOST, Issue №14. Основа проекта: `DSLitvinov1/my_first_repo`. **Кандидат, не установлено, производственная очередь запрещена.**

## 1. Область нового кандидата

Ранее разработанный `offline_os_separated_effect_receiver.py` намеренно ограничен Linux-test окружением, одноразовым соединением и временной базой. В нём нет постоянного производственного процесса. Его нельзя разворачивать на реальном Linux-хосте простым включением тестовых флагов.

В отдельной ветке `neurofactory-host-independent-production-scope-20261018` добавлены только **невыполняющие файловых эффектов** строительные блоки:

- `independent_four_party_scope.py`: четыре отдельные Ed25519 подписи (владелец, оператор прав, HOST, внешний независимый witness), жёсткая привязка к владельцу/GitHub UID/repository ID/исходному коммиту/проекту/задаче/операции/идемпотентности/lease epoch/fence/целевому содержимому. Устаревшее доказательство и поддельная подпись отклоняются. Положительный криптографический результат **никогда не становится правом на выполнение**.
- `operator_installed_public_pins.py`: загрузка четырёх **только публичных** ключей из фиксированного конфигурационного каталога `/etc/neurofactory/trust/four-party-public-pins.json`, принадлежащего root и закрытого от других UID. Нет параметра для замены пути от имени клиента, переменных окружения с ключами, возможности устанавливать/создавать ключи через этот код. Корректность файлового доступа проверяется; физическая принадлежность ключей и подлинная личность оператора требуют внешней проверки.
- `permanent_postgres_operator_migration.sql`: схема постоянного PostgreSQL с `lease_register` и `effect_receipt`. Ограничения на ссылочные/криптографические поля, одно `UNKNOWN` на task, единственный idempotency key, запрет сразу записать `COMPLETED` и запрет обычного изменения/удаления квитанции. Нет временного `nf_test`, паролей, автоматической выдачи PUBLIC-доступа, расширений суперпользователя или автоматического запуска. **Важно:** владелец PostgreSQL способен откатить журнал несмотря на ограничения. Только независимое внешнее неизменяемое хранилище делает повтор после отката запретным.

### Что код не обеспечивает
Он ещё НЕ является защищённым постоянно работающим сервером. Нельзя на основании зелёного CI заявлять действительную личность GitHub-владельца, действительность его текущего доступа к репозиторию, подлинную выдачу аппаратного ключа, защищённую подпись со стороны настоящего HSM, физическую независимость машин, действенность монтирования, внешнюю невозможность отката, подтверждённую перезагрузку и независимое решение REVIEW. Функция четырёх подписей возвращает `live_execution_allowed=false`, `release_approved=false`.

## 2. Действия уполномоченного оператора, не исполняемые в чате

**До установки:** оператор отдельно подтверждает владение/repo ACL через живой аутентифицированный GitHub, назначает владельца и scope проекта, получает отдельное одобрение на два физически разных устройства. Назначает отдельного ревизора REVIEW с независимыми правами на проверку и подпись. Никто не публикует seed, private Ed25519/TPM/HSM ключ, пароль PostgreSQL, recovery-код, mTLS client private key в GitHub/Actions/чат.

**Linux TRUSTED HOST:** установка чистой поддерживаемой Linux, исправления, заблокированный sudo для worker/DB, LUKS/secure boot/TPM (или эквивалентная политика), изоляция namespaces/AppArmor/seccomp, четыре OS UID и отдельный внешний witness **на другом физическом устройстве/вне того же root-домена**. Задать доверенные публичные ключи отдельной процедурой с проверкой fingerprint и отдельным подтверждением оператора; зафиксировать их вне базы и независимый monotonic highwater.

**PostgreSQL (постоянный):** отдельная database instance и роли владельца схемы/reader/lease allocator/effect writer; DBA выполняет миграцию только после ревизии SQL, бэкапа и проверки текущей схемы; никаких сервисных логинов в исходниках, никакого `nf_test`, только operator-controlled secure DSN/service file, TLS и минимальные права. Схема не предоставляет прав PUBLIC и не должна использоваться как единственный доверенный журнал. Для ровно одной операции — внешнее резервирование UNKNOWN ДО записи, повторная центральная проверка lease под блокировкой до fsync и квитанции, независимый witness ack/sequence и защищённое хранение root вне DBA.

**Постоянный получатель:** отдельный безопасный авторизованный системный сервис и проверенный конечный filesystem effect recipient под выделенным непривилегированным UID, а не reuse `offline_os_separated_effect_receiver.py` как production-daemon. Вход только от аутентифицированных доверенных исполнителей через mTLS1.3 + pinned cert/UID, заранее подписанный owner grant, snapshot operator ACL, свежий подпись HOST lease+fence+epoch и независимый witness. Ни CORE, ни модель, ни DB user, ни GitHub Workflow не могут подменить адрес, target, signer key, lease epoch или включить старый writer. Важна атомарность проверки с реальным file-O_EXCL/fdatasync/receipt; при UNKNOWN/сбое ACK — ручная сверка и полный запрет автоматического повтора.

**Запуск:** до подтверждённого REVIEW сервис не должен выполнять рабочие задачи, даже если уже установлены пакеты, systemd unit и база. Настоящий владелец и независимый оператор подтверждают ключи и права, а не позволяют сервису самому выдать себе APPROVE.

## 3. Приёмка и документирование

Пять адресных отрицательных: (1) поддельный/отозванный владелец или чужой repo/source SHA; (2) потерянная/просроченная lease/fencing/epoch; (3) повтор операции после отката PostgreSQL; (4) потеря ACK witness после fsync или авария после записи до квитанции; (5) чужой узел/сертификат/отсутствие независимого свидетеля. В каждом случае 0 НЕРАЗРЕШЁННЫХ эффектов.

Единственная положительная — один инертный файл в заранее выделенном test workspace, созданный привилегированно изолированным HOST после действительных подписей; все защищённые хэши сверены, конкурирующий узел не создаёт второй файл. Один GitHub hosted runner с несколькими UIDs не равен двум физическим устройствам.

**Реальная перезагрузка Linux:** до reboot фиксировать внешние подписи и Linux boot_id, OS-owned ledger/PG highwater и ровно один файл, получить разрешение оператора на полную загрузку, после неё прочитать `boot_id` заново, сверить внешний root/журнал/хэши, восстановить БД из временного снимка и повторить тот же signed operation — никакой второй записи. Проверка внутри одного старта процесса/контейнера не засчитывается. Ни одна машина в текущем сеансе не перезагружалась.

**Независимый REVIEW:** другой уполномоченный человек/идентичность подписывает APPROVE/REJECT отдельно с точными immutable SHA CORE, HOST, COORD, четырьмя публичными certificate fingerprints, ссылками на журналы и двумя independently attested physical IDs. До этого итог `REJECT LIVE`, `HANDOFF PAUSED_BY_USER`.
