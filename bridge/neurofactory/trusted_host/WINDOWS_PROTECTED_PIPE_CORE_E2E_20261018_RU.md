# Windows TRUSTED HOST — защищённый получатель, первый сквозной тест

Дата: 18 октября 2026. Отдельная ветка `neurofactory-windows-protected-receiver-ci-20261018`. **НЕ ПРОИЗВОДСТВЕННЫЙ ВЫПУСК.**

## Что реализовано

1. **Windows ServiceBase-каркас**, проект `windows_receiver/Neurofactory.WindowsReceiver.csproj`. Режим `--service` не выполняет файловых действий, потому что независимая операторская авторизация, долговременные ключи, свидетели и REVIEW ещё не установлены.
2. **Одноразовый изолированный тестовый Windows Named Pipe-получатель**, `windows_receiver/Program.cs`. Создаёт Windows Named Pipe с явной ограничивающей DACL (SID клиента, SID получателя и LocalSystem) без Everyone/Anonymous. При подключении пытается проверить реальный Windows SID через имперсонацию Named Pipe. Весь тестовый процесс на одной GitHub-hosted Windows-машине; совпадающие SID в тестовом режиме НЕ подтверждают изоляцию разных учётных записей в установленной системе.
3. Сверяет закреплённую в тестовом конфиге публичную ECDSA P-256 подпись владельца, точные task/project/source SHA, содержимое, время разрешения, ограниченный путь. Приватный тестовый ключ генерируется только в одном запуске временного GitHub Actions и никогда не пишется в GitHub.
4. В **единственном специально заданном временном каталоге** фиксирует на диске предварительную квитанцию `UNKNOWN` с исключающим созданием, flush/fsync; затем создаёт ровно один безвредный текстовый файл через CreateNew/WriteThrough/Flush(true). Если квитанция уже есть — запрещает повтор, в том числе после перезапуска получателя. Испытание имитирует аварию после записи намерения, но до создания файла: автоматический повтор должен быть запрещён, нужна ручная сверка.
5. `windows_core_pipe_client.py` проверяет существующее состояние и токен **настоящего** `OneTaskCore` из точно закреплённого CORE-коммита `beb08eff32923d8ca364aabfde0458f380acf8e7` (проверяется исходный blob `ab1471813c6da29407c913b974a2209467a4b961`) и передаёт подписанный запрос по Windows Named Pipe. CORE не создаёт конечный файл.
6. CI запускается только на временной GitHub-hosted `windows-2025`, не на домашнем Windows и не на self-hosted Runner.

## Ограничения, которые запрещено скрывать

- Тестовый владелец одобряет учебное задание посредством **временной тестовой** функции; это не настоящая авторизация владельца или live GitHub ACL. Публичный тестовый ключ взят из тестового конфигурационного файла, НЕ из защищённого постоянного корня Windows.
- Отдельный SID не подтверждается при тестах под одним Windows-пользователем. Для настоящей службы требуются выделенная непривилегированная учётная запись/Service SID, жёсткие ACL на Pipe/каталоги/конфиг, запрет контроля службы GitHub Runner, проверка от другого Windows-пользователя.
- Протокол ECDSA P-256 v1 тестовый; старые Linux Ed25519 подписи нельзя молча считать совместимыми. Настоящий владелец должен отдельно подтвердить алгоритм и независимую CNG/TPM-выдачу.
- Локальный receipt не защищает от полного отката диска администратором. Внешняя самостоятельная защита от отката и законная выдача подписанного разрешения до реальных операций не реализованы.
- Защита от reparse/junction для промышленной папки требует отдельного конечного получателя с правильно проверенными file handles/ACL, а не просто этого теста в %TEMP%. Нельзя использовать произвольные путевые аргументы клиента для создания файлов.
- Настоящий постоянный PostgreSQL, атомарная защита аренды до fsync и внешний signed witness не подключены к тестовому Windows ServiceBase. Это план следующей интеграции, не сделанный этап.
- `--ci-one-shot` намеренно доступен только в специальной тестовой среде и создаёт лишь временный файл. Нельзя считать переменную среды источником авторитета: локальный пользователь может подделать CI-переменную, и поэтому никакой реальный путь или ключ не доступен такому режиму.
- Установка службы, реальный перезапуск компьютера, физическая проверка второго устройства, назначение независимого REVIEW, включение очереди и объединение PR **не производились**.

## Матрица проверки

Положительный тест: локальный Git-репозиторий с точным SHA источника, настоящие SQLite `enqueue` и `claim`, проверка client-side token+deadline, единственная ограниченная файловая запись получателем, другая попытка после нового процесса запрещена, CORE sandbox не меняется.

Отрицательные: поддельная подпись владельца; просроченное разрешение; подменённый исходный SHA; попытка traversal `../`; изменённый контент; crash после `UNKNOWN` с повтором после перезапуска; истёкшая локальная CORE-аренда. Никакой тест не авторизует реальное файловое изменение.

## Приёмка следующего этапа

Доработать и независимо проверить реальную Windows службу получателя с выделенным SID, корректной имперсонацией клиента и закрытым конфигурационным источником Windows CNG/TPM. Добавить operator-signed owner scope, внешний monotonic witness и lease/fencing из постоянной базы в сам конечный процесс с непрерывной блокировкой до записи. Затем пять отказов + одна разрешённая пробная транзакция под двумя реальными Windows-пользователями, независимая ревизия. Статус `REJECT LIVE`, `HANDOFF PAUSED_BY_USER`.
