## 2. Входные допуски — без них ЗАПРЕТ

1. Владелец отдельно указывает и одобряет два *физически различных* принадлежащих ему или правомерно авторизованных компьютера, их роли и рамки одной безвредной учебной задачи.
2. Назначенный независимый оператор создаёт/закрепляет уникальные публичные ключи каждого устройства и одного владельца вне CORE, модели, базы данных и временных тестов. Приватные ключи остаются в защищённом хранилище устройства (TPM/OS key store или эквивалентный защищённый источник); не передавать их в GitHub, чат или workflow secrets для тестового сценария.
3. Назначенный независимый ревизор REVIEW — **другая уполномоченная идентичность**, не автор изменения, не исполнитель и не владелец ключа подписанта. Его права на репозиторий и полномочия на REVIEW подтверждены отдельно.
4. Сформирован отдельный защищённый, устойчивый к откату центральный trust-root: GitHub owner/repository/project ACL, разрешённые исходные SHA, назначенные OS/host UID и ключи, внешний monotonic highwater; нет возможности сбросить всё восстановлением той же PostgreSQL.
5. Подтверждены две реально различные доверенные вычислительные платформы, независимые домены хранения разрешений, администрирования и ключей. Один GitHub runner с 3 UID, две VM на одном физическом компьютере и два Postgres соединения НЕ подходят.
6. Ни один шаг реальной записи, перезапуска компьютера или установки без явного допуска владельца. Пока разрешены только read-only проверки, подготовка документации, изолированные disposable CI тесты.

## 3. Обязательный сценарий реального kernel reboot

Выполнять ТОЛЬКО на отдельно выделенном Linux получателе, где уже имеется разрешённый подписанный owner-grant и реально защищённая journal-директория nf_effect. Не перезапускать Windows-PC пользователя ради этого Linux теста.

1. Снять подписанные и точные SHA CORE/HOST, подписанные one-time task/lease/operation ID и challenge от независимого оператора. Привязать публичный ключ и physical attestation к реальному инвентарному узлу. Провести один инертный тестовый файловый эффект с подтверждёнными хешами; никогда не разрешать live проекты.
2. Под `nf_effect` (не из worker/database UID) выполнить `offline_kernel_reboot_evidence.py before` на точном зарегистрированном задании. Зашифрованный отдельно защищённый журнал/квитанция и before boot-id должны быть fsync на энергонезависимый диск ВНЕ PostgreSQL.
3. Зафиксировать независимую внешнюю контрольную сумму состояния; **оператор физически инициирует полную перезагрузку Linux OS**. Не принимать reboot только тестового процесса/контейнера/DB сервиса как эквивалент.
4. После фактической загрузки той же машины и восстановления персональных защищённых прав под `nf_effect` выполнить `offline_kernel_reboot_evidence.py after`: требуется changed kernel boot_id + неизменённая квитанция. Отдельно проверить целевой файл и journal/signer sequence у выделенного получателя.
5. Имитировать откат только временной тестовой PostgreSQL snapshot; повторно доставить тот же подписанный пакет по аутентифицированному IPC. Получатель обязан отказать до второго файла; проверить фактическое состояние protected journal и отсутствие повторных side effects. Проверить тот же сценарий при UNKNOWN (crash after fsync before receipt): ручная сверка, без auto retry.
6. Зафиксировать обе подписанные machine-local квитанции, signed external operator witness, точные SHA, timestamps, hashes и отказные логи. Не копировать закрытые ключи, личные данные или пользовательские файлы.

### Ограничение достоверности
Разница `boot_id` показывает смену загрузки ядра Linux в наблюдаемом окружении, но без внешнего доверенного hardware attestation не исключает подмену среды привилегированным оператором. Не превращать один boot-id proof в RELEASE APPROVED.

## 4. Двухузловая учебная транзакция

1. Оператор независимо подтверждает каждую физическую машину и её закреплённый public key. Создаёт вызов с одним task/source/epoch/operation и двумя независимыми attempt nonces.
2. Одновременно или последовательно отправить одну ограниченную безвредную задачу с обеих физических машин по защищённому каналу. Ровно один HOST получатель должен создать один файл; второй должен получить документированный DENIED с нулём эффектов.
3. Поменять победителя/проигравшего, отключить связь, перезапустить одну OS, повторить запрос после истечения аренды и после отката PostgreSQL. Ни одно действие не должно создать вторую запись.
4. Проверить host-owned signer, независимый owner ACL, external antirollback, failure closed при неподписанном/просроченном разрешении, duplicate op, старом epoch, заменённом target, повреждённой подписи и неверном Git commit.
5. Сверить журналы системы и получателя независимым наблюдателем, signed proof of physical independence и точные post-state hashes.

## 5. Отдельное независимое заключение REVIEW

Только назначенный отдельно уполномоченный ревизор со своей независимой проверкой может решить RELEASE APPROVE либо REJECT. Его заключение должно ссылаться на точные неподвижные коммиты CORE, HOST и COORD, собранные подписи операторов, два настоящих устройства, фактические загрузки системы, post-reboot protected journal readback и 5 отрицательных + 1 успешную учебную операцию. Отчёт авторского GitHub Actions, комментарий в Issue №11 или тест «сам себя проверил» не равен независимому одобрению.

До выполнения всех условий: `REJECT LIVE`, `HANDOFF PAUSED_BY_USER`, никаких paid API, автоматической публикации, моделей в live очереди, слияний веток или реальных файлов клиента.
