# TRUSTED HOST — защищённый журнал вне PostgreSQL и криптографический прототип допуска владельца
Дата: 17 октября 2026. Статус **CODE+NEW TARGETED CI PASS, NOT PRODUCTION AUTHORITY**.
Владелец TRUSTED HOST (Issue #14 / DRAFT PR #15). Точный изменённый source pinned по blob-объектам, а не только по последнему коммиту.

## 1. Практическое закрытие отката PostgreSQL без второго необратимого эффекта

Новый `bridge/neurofactory/trusted_host/offline_recipient_protected_journal.py`, blob `578e2114c971529039d9a3e151c0fe37c103cfa1`. Это **второй durable журнал**, который создаёт только OS UID конечного получателя `nf_effect`, в закрытой им директории `nf-recipient-config/nf-protected-effect-journal` с 0700/0600. Ни DB user, ни CORE/модель не владеют этим каталогом. Journal держит OS `flock` при попытках двух конкурентных операций. Блокирующие маркеры для `task_id` и нормализованного `target` создаются O_EXCL/O_NOFOLLOW, fsync файла и родительского каталога, **раньше, чем PostgreSQL UNKNOWN intent и файл**, так что rollback/restart PostgreSQL не открывает автоматический повтор. Начальное состояние `UNKNOWN_MANUAL_RECONCILIATION` и проверяемый exact SHA эффектного содержимого. После подтверждённой единственной операции отдельная атомарная durable запись переводит task marker в `COMPLETED_TEST_ONLY`, target marker продолжает запрещать повтор. При любой аварии UNKNOWN остаётся и блокирует новый эффект до отдельной ревизии; никакого автоматического ручного снятия маркеров нет.

Подключено в реальную TEST ONLY цепь через `offline_operator_gated_receiver.py`, blob `db8a6413d01705adff4726d4c10e08603ea720aa`, и `offline_os_separated_effect_receiver.py`, blob `fa9e5eab68a9e669ce64a05e61243a17dddbcd48`. Это обязательный новый шаг **для изолированного OS-receiver** (старый прямой test-only callable остаётся для прошлых фикстур, но обычный worker не может открыть защищённую директорию nf_effect). Сначала проверяется signer-owned exact scope; затем создаётся защищённый durable UNKNOWN; после него receiver сам вновь проверяет живые lease/fence/worker/source/PG journal и делает O_EXCL fsync. У клиента нет права выбирать persistent ledger root.

**Адресные реальные Ubuntu24.04 + PostgreSQL16 тесты**:
- [GitHub Actions №39065132995](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39065132995), job `117491061207`, exact tested HOST SHA `6726d2c7dc6e852ae63a780c899914602f65978e`: **3/3 PASS**. Настоящий одноразовый файл создан; DB effect journal удалён и **сам файл удалён отдельно разрешённым испытательным оператором**; перезапущенный OS receiver отказал в новом эффекте благодаря внебазовому защищённому journal. При экспериментальном аварийном отказе после fsync, до DB receipt файл существует, OS protected state = UNKNOWN; после перезапуска receiver и удаления PostgreSQL journal отказал в повторе. Рабочий DB actor не смог открыть/стереть защищённые журналы.
- [GitHub Actions №39065521267](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39065521267), job `117492250518`, exact tested HOST SHA `e23d9a0bd83b662b71a8988494f4faadf11d7ce4`: **4/4 PASS** (3 актуальных rollback/crash/UID сценария + 1 новая конкуренция). Два независимых процесса ОС одновременно запросили расход одной task/target; **ровно один** получил защищённый claim, второй DENIED; маркер остался durable. Ни один прежний полный CORE–HOST/Qwen набор в финальный целевой прогон не включён. Все эти проверки — одна физическая ephemeral CI-машина с разными Linux UID, не multi-host power-cut.

Ограничение: root и compromised nf_effect UID всё ещё смогут уничтожить защищённую директорию; внешне подлинно удостоверенное immutable highwater/backup на отдельном физическом trust domain отсутствует. Текущий журнал защищает **от админа одной PostgreSQL БД/worker UID**, но не от оператора с root/nf_effect и не от отката всего VM/диска. Целевой recipient тестовый, не установленный сервис. На реальном пользователе НЕ проводились install/reboot/ACL mutations.

## 2. Подпись владельца и независимая предварительная регистрация разрешённых ключей

Новый `bridge/neurofactory/trusted_host/offline_owner_grant_admission.py` blob `fbe8a1f1d00c07e94f80d48bb8289b64887c85bc`, тест blob `61ff4ba311c53c22f3a69f52eec574486d327c12`. Signer UID принимает только owner-key, который заранее закреплён в принадлежащем подписанту `0600` allowlist, расположенном ВНЕ PostgreSQL и worker filesystem. Проверяется настоящая Ed25519 owner-подпись на точных owner_id/repo/project/task/worker/source SHA/target/operation/lease epoch/permit digest и строгом сроке действия. Подмена подписи, параметров и попытки DB worker переписать pin получают отказ. **Никакой caller-controlled pubkey** и никакая положительная текстовая строка не становятся авторизацией.

[GitHub Actions №39065429957](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39065429957), job `117491974573`, exact tested HOST SHA `f42f692c30ebbe9ab62279b5e9c12be153891842`: **6/6 PASS**. В этих случаях временный "владелец" — лишь тестовый Ed25519 ключ, а операторский pin — тестовый файл; НЕ доказаны юридические полномочия реального владельца, доступ GitHub repo admin, право запускать очереди или общий рабочий project ACL.

**Важно: модуль owner-grant — самостоятельный предэксплуатационный verifier, пока НЕ подключён как обязательный owner enrollment gate в TEST/PROD файловый receiver.** Делать вывод «настоящий владелец проверен» НЕЛЬЗЯ. Перед подключением потребуется внешнее удостоверение owner ID и прав на конкретный repo у уполномоченного оператора, вне репозитория/чата; подписант и OS recipient обязаны принимать только pinned enrollment и актуальную owner-grant подпись для каждой операции. Установка настоящих закрытых ключей или root доверия в Actions запрещена.

## Что осталось и кто должен подтвердить

- **HOST:** в отдельном разрешённом оператором процессе установить действительно независимый постоянный signer/key custody, owner-repo registration + revoked owner ACL, persistent receiver UID и внебазовый защищённый root на диске с устойчивым rollback highwater за пределами того же физического хоста. Для реального production случая без этих условий политика FAIL-CLOSED.
- **CORE/PROVIDERS:** следующий реальный execution-provider должен генерировать новую программу в рамках действующей центральной аренды, а не копировать ранее verified Qwen SHA. Практический учебный historical Qwen→CORE→HOST на одном runner пройден ранее (#39064047131), но LIVE заблокирован.
- **OPS:** резервная копия и реальное восстановление после физического reboot/power loss двух разных компьютеров НЕ выполнены. Нужны проверки состояния protected ledger и root pins после восстановления, не только PostgreSQL.
- **REVIEW #11:** запрос отдельному реально уполномоченному человеку на точных SHA+Git blobs, угрозы alternate raw API, UID=root/nf_effect, replay DB and full VM snapshots, credential provenance и signed independent verdict. Второй чат/автотест не равен независимому допуску.
- **COORD:** статус глобального выпуска BLOCKED, HANDOFF PAUSED; нет платных API, merge, production queue или публикаций.
