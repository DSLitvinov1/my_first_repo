# HOST — отдельный подписант → проверка owner-scope → конечный PG/Fsync файл (НЕ LIVE)
17 октября 2026. Владелец TRUSTED HOST, Issue #14. Все факты ниже относятся ТОЛЬКО к ephemeral GitHub-hosted Ubuntu 24.04 runner, PostgreSQL16 nf_test и временным Linux UID nf_signer / nf_db_actor. Не признавать production owner approval или производственный issuer.

## Новые работающие компоненты

1. `offline_signer_scope_guard.py` Git blob `6906a2769f563a0269c264a4c153882c53d2d9ab`: отдельно signer-UID-owned policy `0600` содержит строгое соответствие issuer/key, владелец, репозиторий, проект, task, worker, исходный Git SHA и хеши, policy, target, proposed bytes, fence, lease epoch, operation и idempotency. Отклоняются любые отличия, включая повторную подпись другого содержимого. Ed25519 разрешения проверяется по issuer-public, хранимому у подписанта, не по переданному caller ключу. Signer highwater проверяется по latest signed current tip и хешу полного permit. Источник Owner policy в этих тестах — **временный оператор теста**, не человек с подтверждённым владением. Результат всегда только `OWNER_SCOPE_FIXTURE_MATCHED_NOT_AUTHORITY`.
2. `offline_operator_ipc.py` Git blob `651277394acc0869ff628c8578300818a23e55be`: Unix-socket `SO_PEERCRED` со стороны сервера проверяет клиента nf_db_actor; со стороны клиента обязательное pin-аутентифицирование UID сервера. Group directory теперь **2750**, не group-writable, запрещена подмена path внутри общего каталога. Ключ подписанта никогда не передаётся клиенту. Можно запросить только read-only checkpoint/scope verdict с `filesystem_write_allowed=false`.
3. `offline_operator_gated_receiver.py` Git blob `f4af58853773192c82142794aadd48be48e5b2fe`: тестовый gate сначала требует полномочия из защищённого подписанта по pinned Unix UID, затем вызывает существующий реально файловый PostgreSQL16 HOST recipient. Нижний receiver заново независимо проверяет подписанный scope, текущий PG lease, worker, epoch, fence и single-use journal UNKNOWN, пишет только новый scratch файл через O_EXCL/O_NOFOLLOW и fsync, подтверждает квитанцию. При ложном/отсутствующем ответе подписанта gate блокирует вызов receiver; при UNKNOWN/replay propagates deny. Все флаги live/retry/owner authority false. **Старый test-only receiver можно вызвать напрямую в пределах этой же учебной среды — никакой OS-protected единой производственной точки записи пока нет.**
4. CORE не редактировался: legacy прямой writer отключён; тестовая CORE→HOST интеграция на прежнем SHA сохранена без повторов. Нет remote mTLS сервиса или реальной постоянно закреплённой operator root identity.

## Непреодолённые выпускные блокировки
**REJECT LIVE**. Owner policy и root signer пока provisioned в ephemeral CI от доверенного теста, НЕ проверен human owner/repo ACL с независимой цепочкой полномочий. Корень доверия и приватный ключ не установлены на долгоживущем собственно доверенном сервере. Базовый test-only HOST receiver технически callable напрямую тем же Unix principal; нет OS-isolated real effect destination без этого обхода. Подмена выполняемого тестового Python кода при root компрометации остаётся вне модели. Нет устойчивой защиты владельца/репозитория от privilege escalation, пользовательского аппарата и восстановления после reboot, двух независимых физических компьютеров, реального CRASH+rollback на них, независимого подписанного допуска ревизора. Qwen генерация ранее выполнена отдельно, не в одной с этой связкой проверенной операции. Никаких платных API/публикации/слияния веток/HANDOFF.

Следующий этап: отделить конечный receiver в отдельную ограниченную OS службу, физически запретить обходной прямой writer пользователю CORE/DB/model, provisioning из независимо удостоверенного operator-owned allowlist/ключа, protected server UID и machine identity, аутентифицированный host transport; проверить на 2 реальных уполномоченных физических машинах + независимая приёмка exact SHA, затем allowed untrusted Qwen proposal into receiver только после центральной авторизации.
