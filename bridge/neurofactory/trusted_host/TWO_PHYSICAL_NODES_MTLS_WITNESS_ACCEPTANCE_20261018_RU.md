# №17 — подготовка настоящего межмашинного свидетеля TRUSTED HOST и двух физических ПК

Дата: 18 октября 2026. OWNED BY TRUSTED HOST, Issue №14, DRAFT PR №15. Статус: **ПОДГОТОВЛЕНО И ПРОТЕСТИРОВАНО ТОЛЬКО НА ОДНОМ ВРЕМЕННОМ LINUX RUNNER. СЛУЖБЫ НЕ УСТАНОВЛЕНЫ, LIVE ЗАПРЕЩЁН.**

## Текущее доказательство
В репозитории новый экспериментальный протокол `bridge/neurofactory/trusted_host/offline_mtls_witness_transport.py`: TLS 1.3 с обязательной клиентской и серверной аутентификацией, действительной цепочкой сертификатов, проверкой DNS-имени сервера, привязкой ТОЧНОГО DER SHA256 fingerprint сервера и клиента, кратким ограниченным протоколом запрос/подписанный ответ. Даже сертификат подменного клиента, подписанный той же тестовой CA, отклоняется по несовпадающему сертификату. Сервис свидетеля до подтверждения создаёт и синхронизирует на диск независимые от рабочей PostgreSQL маркеры операции и цели; потерянный ACK не допускает автоматического retry. Клиент также проверяет независимую Ed25519 подпись ACK свидетеля по заранее закреплённому открытому ключу и точному digest/nonce/target/task.

Протокол ЗАПРЕЩАЕТ публичный сервер в текущем исходнике: слушает `127.0.0.1`, требует явный флаг `NF_MTLS_WITNESS_TEST_ONLY=1`, принимает один запрос; не содержит пользовательской учетной записи, реального remote-daemon или права на рабочие файлы. Это сознательный безопасный тестовый прототип перед разработкой отдельного авторизованного network-deployment wrapper. В GH Actions не передавались реальные закрытые ключи. CA, сертификаты клиента/сервера и witness Ed25519 были созданы только на время теста. Свидетель и получатель действуют как ДВА разных Linux UID на ОДНОЙ машине.

Новые Linux-hosted испытания: [Actions #39071907860](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39071907860), job `117511086200`, exact tested source commit `87409fe15543f47f1d6318aaa220b4f547631270`, **6/6 PASS**:

2. неправильный закреплённый fingerprint сервера останавливает запрос ДО эффекта;
3. неправильный публичный Ed25519 ключ свидетеля отвергает ACK, даже если маркер уже создан — только UNKNOWN, без нового эффекта;
4. потеря ACK после fsync свидетеля блокирует повтор;
5. недоступность сервера завершает запрос отказом;
6. второй клиент с ДРУГИМ действительным сертификатом той же CA не получает доступ из-за строгой привязки конкретного DER сертификата.

Ни один из этих тестов не доказывает криптографическую/физическую защищённость второй реальной машины. Предыдущие 14/14 owner proof и OS witness [GH #39068798565](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39068798565), 3/3 real recipient v2 [#39069156061](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39069156061), полная регрессия 25/25 [#39069220676](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39069220676) остаются принятыми как **TEST ONLY**. В текущем релизе TLS network adapter ещё НЕ подключён как обязательный endpoint конечного файла — V2 использует Unix socket на одном тестовом runner. Не подменять это реальной сетью двух физических устройств.

## Реальная процедура после письменного разрешения на оба независимых устройства
**Входные требования**: отдельно идентифицированный GitHub owner + независимый уполномоченный оператор; два устройства с разными физическими идентичностями под законным контролем и явным разрешением на администрирование; независимые user/OS роли, отдельный backup носитель для witness; документированное окно тестов и обратимый план восстановления. В данный момент список подключённых пользовательских ПК содержит только `WIN-LIDC05TBOQD` (online), второй не подтверждён.

1. Владелец на защищённом, не подключённом к чату хранилище генерирует приватный owner Ed25519 key. НЕ пересылает private key и recovery фразы в ChatGPT, GitHub, Issues, logs. Оператор независимо проверяет stable numeric GitHub user/repo IDs, актуальный admin permission и repo metadata через официальный API, применяет TTL/revoke-policy. Владелец подписывает случайный короткоживущий challenge со scope/path/source и fingerprint публичного ключа. Уполномоченный оператор подписывает отдельный снимок GitHub ACL. Оба доказательства и одноразовый nonce закрепляются вне PostgreSQL.
2. На **машине Б — witness**, независимо авторизованный оператор создаёт отдельную системную роль с минимальными привилегиями и отдельным durable write-once/append-only состоянием, сохраняет зашифрованный witness signing key и внешнюю контрольную точку, защищённую от администратора машины А. Публичный fingerprint root вручную сверяется по независимому каналу. Witness-узел не должен иметь прав менять проекты/файлы владельца.
3. На **машине А — HOST/recipient**, отдельный nf_effect UID владеет только разрешённой песочницей и приватной конфигурацией; DB/operator/CORE/модель не получают прав каталога. Раздельный оператор выпускает serverAuth сертификат с точным SAN имени свидетеля и clientAuth сертификат для авторизованного receiver, с явной привязкой стабильной machine identity, pinned CA и pinned exact DER SHA, сроком годности/ротацией/отзывом. Сертификатные private keys на своих разных машинах — 0600/OS keystore, никогда в репозитории. Не использовать тестовый CA в работе.
4. Прежде чем разрешить сетевой доступ, отдельный аудитор проверяет bounded network server adapter, firewall allowlist или отдельную VPN/приватную сеть, mutual TLS handshake, pinned peer identities, дубликаты peer sessions, bounded resource quotas и fail-closed при revocation/expired cert/network loss. Текущий TEST ONLY `127.0.0.1` модуль НЕ следует просто запускать как общедоступный сервер; полноценный remote listener требует отдельной разработки, проверки и утверждения.
5. На машине А разрешается ОДНА синтетическая задача с точной текущей центральной арендой. Перед локальным fsync файла witness машины Б должен подтвердить fsynced UNKNOWN marker по точным permit SHA, owner ID, repo ID, task, operation, target и lease epoch. При задержке, потере ACK или недоступности witness — `UNKNOWN_MANUAL_RECONCILIATION`, без автоматической повторной записи.
6. Аудитор фиксирует независимые контрольные суммы и записи двух машин, затем с разрешения владельца ВЫКЛЮЧАЕТ/ПЕРЕЗАГРУЖАЕТ только машину А и восстанавливает старый снимок локальной базы/файла/состояния recipient. Машина Б при этом НЕ откатывается и сохраняет собственный журнал, ключи, последовательность. Второй запрос на ту же цель/операцию должен быть отвергнут внешним witness, число настоящих внешних эффектов не увеличивается.
7. Аудитор отдельно имитирует отключение witness Б и подтверждает остановку А, подменяет сертификат сервера/клиента и проверяет отказ, тестирует recovery после fsync до DB receipt и конкурирующий вторичный исполнитель. Подписывает exact code SHAs, machine IDs без публикации серийных номеров, уровни доступа, временные отметки, публичные thumbprints, результаты fail-closed и решение `APPROVED_NARROW_TEST` либо `REJECT`.
8. Дополнительный критический тест: rollback самой машины Б / компрометация root или единственного witness UID. ДВА компьютера сами по себе не защищают от одновременного отката обоих; требуется третий независимый WORM/hardware monotonic seal или иная доверенная внешняя контрольная точка. Без неё нельзя заявить гарантированную anti-rollback при полном двустороннем компромиссе.

## Критерий сдачи на эксплуатацию

Есть независимо подтверждённый настоящий владелец и закреплённые настоящие ключи, безопасный межмашинный endpoint на двух различных разрешённых компьютерах, независимый witness не откатывается с HOST, после настоящего физического reboot+backup restore повтор не создаёт эффект, сформирован отдельный подписанный REVIEW verdict по точным SHAs и дано отдельное разрешение владельца на production. До выполнения ВСЕХ этих условий: **REJECT LIVE; очереди OFF; HANDOFF PAUSED; no paid API; no merge; no user PC changes**.

## Новый шаг: протокол привязан к конечному файловому эффекту в изолированной версии V3

Существующий `offline_operator_gated_receiver.py` дополнен отдельным строго учебным вариантом mTLS. Файловый получатель `offline_os_separated_effect_receiver.py` допускает схему `neurofactory.os_separated_recipient.mtls_loopback_fixture.v3` лишь с полным закрытым recipient-owned configuration: клиентским сертификатом, приватным ключом 0600, доверенной CA, pinned SHA-256 сертификата свидетеля и pinned Ed25519 public key для его ACK. Модель, CORE и администратор рабочей PostgreSQL не могут из своего запроса заменить ни ключ, ни адрес, ни каталог. Прежде чем изменить один временный файл, получатель проверяет owner-signed permit в отдельно запущенном подписанте, затем принимает ТОЛЬКО подписанное подтверждение witness через взаимный TLS; при отсутствии ответного сообщения, несоответствии доверенного сертификата или повторе операции эффект не создаётся.

Новые испытания [Actions №39072452851](https://github.com/DSLitvinov1/my_first_repo/actions/runs/39072452851), job `117512685528`, exact tested HOST SHA `e726d87ec28677c710fad0b2facb0530358f153f`: **3/3 PASS**, включая actual test file после owner+signer+mTLS+remote witness+PG, затем умышленный откат локального PostgreSQL-журнала, recipient-owned markers и удаление test file, но witness на отдельном UID сохраняет запись и запрещает повтор. Другие два: потеря ACK после witness fsync предотвращает любую запись, подмена pinned TLS server certificate SHA запрещает эффект до внешнего резервирования. Эти эксперименты в одной временной Ubuntu-машине GitHub-hosted с несколькими OS UIDs, а НЕ физическими двумя ПК, и не настоящая внешняя сеть.

**Реальное межмашинное размещение этого тестового V3 ещё запрещено**: сервер принимает только loopback-соединение, а сертификаты и ключи формируются как одноразовые тестовые, не удостоверены реальным владельцем и независимым оператором. Будущий производственный TCP listener, его доступ из частной сети и mTLS machine trust/policy должны пройти самостоятельную проверку на двух явно авторизованных физических компьютерах. Ни один live-контрольный сервер не был опубликован и ни одна служба не установлена.
