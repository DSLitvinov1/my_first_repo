# НЕЙРОЗАВОД — приёмка внешнего свидетеля для Windows (пилот, НЕ production)

Дата: 18 октября 2026. Исполнительский кандидат: отдельная ветка `neurofactory-windows-external-witness-pilot-20261018`, основание Windows DRAFT PR #19. Все изменения являются только исходными файлами и GitHub-hosted учебными тестами; никакой установки и перезагрузки пользовательских компьютеров не было.

## Архитектура и граница доверия

Устройство A — отдельно авторизованный Windows CORE/Receiver, worker не должен иметь файловые или ключевые права получателя. Windows Named Pipe принимает один инертный подписанный запрос. После проверки подписи владельца HOST создаёт защищённую локальную запись UNKNOWN, обращается к отдельно аутентифицированному свидетелю по TLS 1.3 с клиентским сертификатом и строго закреплённым сертификатом сервера, проверяет Ed25519 подписанное подтверждение резервирования и только после этого выполняет CREATE_NEW/эксклюзивную запись и fsync. Любая неопределённость по сети = ручная остановка, никогда не retry.

Устройство B — **другой физический Windows-компьютер или независимо управляемый сервис с отдельным администратором**, где размещён свидетель. Подписывающий закрытый ключ B никогда не передаётся A, его worker или GitHub Runner. B сохраняет на своём независимом носителе последовательность, журнал одноразовых операций, отпечаток цели и цепочку SHA, подтверждая результат только после записи. Откат локальной БД или диска A не должен откатывать состояние B. Простой второй процесс на A, GitHub-hosted Windows runner и два виртуальных окружения не удовлетворяют этому требованию.

**Текущий код намеренно ограничен `NF_WINDOWS_WITNESS_TEST_ONLY=1` и временными каталогами; он не проверяет аппаратный TPM, Windows service SID и DACL, полноту сертификатной политики, полномочия настоящего owner/operator или защиту самого B от отката. SQLite FULL-синхронизация подтверждает только свойства учебного процесса, но не обеспечивает неизменность против администратора B и физической копии его диска. Ни service installation, ни реальное удалённое прослушивание пока не разрешено.**

## Предусловия для реального развёртывания (на сейчас НЕ ПОДТВЕРЖДЕНЫ)

- Письменное одобрение владельцем *двух* физических устройств с их раздельными удостоверенными отпечатками, инвентарными номерами, ролями A/B и назначением независимого администратора B.
- Вне исполнения CI уполномоченный оператор самостоятельно создаёт долгосрочные ключи, подтверждает права владеющего GitHub owner/repo, PIN trust roots, ротацию/отзыв сертификатов, срок действия и CNG/TPM/ключ-хранилище. Никаких ключей не пересылать через комментарии GitHub или чат.
- Отдельные локальные учётные записи/Service SID, реально подтверждённые ACL диска, Named Pipe DACL и audit log. GitHub self-hosted worker не является доверенным подписантом.
- Надёжный канал mTLS между A и B, закреплённые сертификаты и отдельное защищённое monotonic/append-only хранилище B за пределами бэкапов и полномочий администраторов A.
- Подтверждённый независимый REVIEW конкретных SHA, включая внешний протокол и поведение после настоящей перезагрузки.

## План строго фактических испытаний на двух разрешённых устройствах

Все действия только после отдельного разрешения владельца/REVIEW на ограниченный тест. Использовать один разрешённый тестовый инертный файл в изолированной зоне, запретить реальную модель, проекты, публикацию, paid API, HANDOFF, live очередь.

1. **Отказ 1 — ложное разрешение владельца:** фальсифицировать *учебный* запрос, проверить отказ до резервирования свидетеля и отсутствие файла.
2. **Отказ 2 — чужой субъект/клиентский сертификат:** отдельное неправильное SID или TLS клиентское удостоверение, отказ до write/remote reservation.
3. **Отказ 3 — истёкшая аренда и неправильное fencing:** отменить/истечь тестовую lease, HOST/CORE должны отклонить операцию, даже если остальной пакет подписан.
4. **Отказ 4 — потеря подтверждения после устойчивого резервирования:** B сохраняет UNKNOWN, обрывает ответ; A не пишет либо помечает UNKNOWN, повтор запрещается даже после настоящего перезапуска A.
5. **Отказ 5 — откат локальной БД/файла и повтор:** зафиксировать B highwater и журнал, затем восстановить только резервную копию A; после **настоящей** перезагрузки A второй эффект блокируется B. Обязательно доказать, что журнал B остался неизменным и активная lease вновь проверена.
6. **Единственная положительная транзакция:** свежая аренда, все настоящие сертификаты и четыре роли, новое неповторявшееся поручение, подтверждение независимого B, одна запись инертного файла A, квитанция и проверка хэша. После настоящей перезагрузки обеих машин никаких новых файлов при чтении журнала.

Для каждого из шести сценариев фиксировать: точный SHA CORE/HOST/WITNESS, снимки PIN идентичностей без секретов, идентификатор разрешённой машины A и B, реальные время/причину перезагрузки ОС, OS boot ID/uplink, журнал B до/после, хэш тестового файла A до/после, статус аренды, системный exit code, отдельные reviewer signoff. «Процесс завершился и запустился» **не** заменяет проверку настоящего перезапуска Windows.
