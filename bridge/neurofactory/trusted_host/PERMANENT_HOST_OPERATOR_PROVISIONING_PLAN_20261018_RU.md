## Почему сейчас нельзя выполнять постоянную установку

Учебный код использует токены окружения/тестовую БД/пробную подпись, без постоянной сертифицированной принадлежности репозитория, защищённого хранилища ключей и криптографически независимого источника монотонной последовательности. Установка этих исходников как реального сервиса создала бы ложную уверенность в безопасности. **Ни один тест и скрипт этого пакета не поднимает службу, не создаёт ключей, не устанавливает пакеты, не изменяет компьютер, не перезагружает ОС и не разрешает живые задания.**

Read-only предустановочный аудит: `python3 -B bridge/neurofactory/trusted_host/deployment_readiness_preflight.py --repository .`. Возвращает JSON отчёт и код завершения **2**, пока кандидат не перешёл к независимой производственной аттестации. Выходной код 0 **намеренно невозможен**: наличие двух подписанных тестовых квитанций не доказывает полномочия оператора.

## Порядок подготовки двух физических устройств

### 1. Авторизация оборудования (оператор, не ИИ-агент)
Нужны два отдельно выделенных *действительно физических* компьютера с правом удалённого доступа, подтверждённым владельцем. Узел А должен быть Linux TRUSTED HOST; узел Б — отдельным разрешённым испытательным клиентом. Один компьютер и VM, два пользователя, два GitHub runners на одном сервере, общий Windows-процесс или два порта одного компьютера **не засчитываются**. Фиксировать серийные номера, TPM и физический инвентарь только в защищённом реестре оператора; в GitHub помещать только проверяемые SHA-256 сертификатов и анонимизированные идентификаторы.

### 2. Реальные ключи и полномочия
- Администратор оператора вне CORE/модели и вне GitHub Actions подтверждает, кто владелец репозитория/проекта и кто уполномочен подписывать операции. Проверять через настоящий GitHub identity/ACL и отдельно подписанное согласие владельца. Не принимать текст в задаче, chat-сообщение, test callback, обычный GitHub Issue или claim в PostgreSQL за криптографическое доказательство полномочий.
- Отдельный подписант имеет приватный Ed25519 ключ в TPM/HSM/защищённом OS хранилище, не экспортируемый под worker, DB или receiver UID. Никогда не записывать приватные ключи/seed/API token в Git, CI, Slack/Telegram, чат, stdout, журнал, временный test-runner.
- На стороне каждого физического устройства — собственная независимая пара ключей и заранее закреплённый доверенный публичный ключ. Изображение экрана, строка с ключом от потенциального атакующего, подставленная переменная окружения и test PEM не создают авторизации.
- Отдельная роль уполномоченного REVIEW не совмещается с подписантом, владельцем кода CORE и создателем подтверждений.

### 3. Защищённый Linux HOST (только после отдельного назначения)
- Чистая поддерживаемая Linux LTS ОС, включённые обновления безопасности, безопасная загрузка, полнодисковое шифрование или эквивалентные аппаратные гарантии, периодически проверяемый аудит, брандмауэр с минимальным списком адресов.
- Системные роли: выделенный оператор ключей, непривилегированный worker, отдельный UID получателя эффектов, отдельный UID внешнего свидетеля с собственным root of trust. Ни worker, ни DB, ни модель не могут повысить права до этих UID; права на папки и сокеты проверяются, не полагаясь на одного root пользователя.
- Постоянные каталоги/private config (0600/0700), отдельное защищённое хранилище журнала и off-host immutable highwater. Независимый witness должен жить в ИНОМ доверенном домене, а не только в отдельном UID на том же физическом HOST. Ключи подтверждения не передавать между ними.
- Только после завершения архитектуры: постоянный IPC/mTLS сервер, который проверяет доверенную личность владельца, task/project/repo/source SHA, code content hash, policy, worker, lease epoch/fencing id, timeout/idempotency, подписанное разрешение непосредственно перед атомарным эффектом. Запись производит только выделенный получатель, не CORE. Нет совместимости с тестовым отключателем или тестовой базой `nf_test`.
- Запустить sandbox/контроль защиты внутри системы (no-new-privileges, ограниченные Linux namespaces/capabilities, seccomp/AppArmor, изоляция доступа на чтение/запись, ограничения ресурсов, CPU/RAM/VRAM), не разрешая работу с реальными проектами без внешней подписи и REVIEW.

### 4. Доказательство настоящей перезагрузки (НЕ выполнялось)
- До reboot независимый оператор и выделенный effect UID фиксируют уже разрешённую инертную транзакцию, fsync результата, protected journal, подтверждение внешнего свидетеля, SHA всех компонентов, before Linux `boot_id`.
- Независимо разрешённый администратор проводит **реальную перезагрузку физического Linux-компьютера**. Одна команда stop/start, docker restart, новый runner или reconnect по SSH не заменяют reboot.
- После boot независимо проверяют изменившийся boot_id, тот же protected journal, неизменные hashes и законность ключей. Отдельно выполняется откат тестовой PostgreSQL и повтор того же пакета: 0 новых файлов и квитанций. После fsync-before-receipt — UNKNOWN и только ручная сверка.
- Read-only тестовый `offline_kernel_reboot_evidence.py` уже умеет отвергать имитацию reboot на прежнем boot-id. Он ещё не производственный trust-root и не заменяет аппаратную аттестацию.

### 5. Транзакция двух реально различных физических узлов
Пять обязательных отрицательных испытаний: (1) поддельная или отсутствующая подпись владельца, (2) устаревшая аренда или wrong fencing epoch, (3) повторный идентификатор операции после SQL rollback, (4) отказ внешнего witness/утрата квитанции после fsync, (5) запрос со второго неавторизованного устройства или изменённым source SHA/target. Для каждой — 0 непозволенных эффектов.

Единственная положительная операция: оба авторизованных физических узла наблюдают один ограниченный учебный task; победивший получатель записывает ровно один инертный временный файл, второй наблюдает DENIED. Сравнить публично проверяемые SHA, idempotency, защищённый журнал и физические инвентарные доказательства. Никаких реальных пользовательских исходников, автоматической публикации, оплачиваемых API, авто-merge, live очереди или HANDOFF.

### 6. Передача в REVIEW и прекращение BLOCKED
Передать ревизору на другой уполномоченной личности неизменяемый пакет: точные commit SHA CORE/HOST/COORD/REVIEW, подписи/публичные ключи, независимое подтверждение реальной принадлежности устройств, before/after boot, receipt/journal hashes, записи запрещённых попыток и матрицу результата 5 отрицательных + 1 положительная. Вердикт обязательно связывается с конкретными коммитами, а не с названием ветки. **Только** независимая подписанная приёмка и прямое разрешение владельца могут изменить статус `REJECT LIVE`.

## Как пользоваться подготовленным preflight

Оператор может скачать Git исходники только после проверки repo ACL/commit SHA, затем запустить read-only модуль. Результат `BLOCKED_EXTERNAL_ATTESTATION_REQUIRED` — ожидаемый и правильный, пока реальные ресурсы не предоставлены. Нельзя вручную изменить JSON-флаг `release_approved` или env `NF_*FIXTURE_ONLY` и тем самым получить право устанавливать HOST.

Отдельная ветка содержит только preflight, тесты и этот план. Без изменения основной ветки, ключей, базы, операционной системы и сервисов.
